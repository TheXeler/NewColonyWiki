Building design system

Building designs are sparse semantic documents compiled into authoritative block cells. Object order is significant: later objects replace earlier cells, deletions reveal the preceding object, and explicit cell overrides are applied last. A design has no editor canvas size limit.

Block metadata

Every block with placeable: true must declare palette_category, palette_order, a non-empty duplicate-free allowed_directions array, can_support, positive construction_task, and positive durability_contribution. Optional building_capabilities are attached to the block cell. Invalid metadata rejects the mod data record.

Direction and persistence

Block direction is a six-way value: east, west, up, down, north, or south. It is independent of the legacy data byte. Chunk palettes, region files, network chunk deltas, live block updates, and model rendering retain this value. Region and network formats intentionally reject the previous format; this pre-release subsystem has no compatibility adapter.

Compilation and support

Compilation derives bounds, one matching item per cell, total work, total durability, capability points, and direction validity. Whole-building rotation changes horizontal coordinates and directions together.

Blueprint content IDs use BLAKE3-256 over deterministic canonical binary content. The local library filename is intentionally excluded, so renaming an identical blueprint does not duplicate world content. There is no legacy digest compatibility path.

Natural solid cells seed support from below or the eight same-level neighbors. Supporting player blocks propagate through eight-neighbor horizontal steps for distance zero through seven, and vertically upward. Non-supporting cells may terminate a supported path but cannot propagate it. Missing neighboring chunks produce a pending result rather than air or collapse.

Construction core

Success is determined from the submitted request's confirmed cells when a pass encounters placement failures. Posting an older request cannot turn a wholly unsupported new request into a success. A successful placement within a block group preserves the rejection reason for that group's unsupported cells. The submitted statistic still counts work posted across the whole pass.

systems.block_placement.designate returns cells containing the coordinates that acquired work, alongside ok, count and reason. A partially successful placement confirms those cells immediately; the design queue retains only the unsuccessful cells for later passes. Returned coordinates are independent of the saved placement records.

A submission that resolves any of its own already ordered or built cells returns those confirmations even when other cells are still unsupported. It reports a partial result while the retry queue remains nonempty. Resolving cells from a different request does not count toward this request's confirmed cells. A request with no newly posted or confirmed cells still reports the placement failure.

The server design queue rejects nested calls to submit, update, reset or restore while another queue operation is running. Placement callbacks and state access cannot replace a candidate queue in progress. The guard is released after success or error; an error preserves its original Lua value. Queue persistence failures retain entries for reconciliation on a later pass, but placement and queue persistence do not yet form one atomic transaction.

The construction plan exposes a lazy ready frontier. Each cell reserves one item instance and commits only after its own work completes. Cancellation releases uncommitted reservations and exposes completed cells for top-down demolition. Player block ownership is stored separately from block identity so natural and player-built blocks with the same ID remain distinguishable.

RmlUi

The Door and Window tools are combined into a single Chisel tool (core:building_design.tool with tool: "chisel"). Hovering a draft block previews the cells to remove in red. Click for one horizontal cell column, or drag between draft blocks to select a rectangular horizontal footprint; the selected height extends the cut upward from the first block's layer. The height buttons and mouse wheel adjust that height. Start at the bottom of a wall to carve a door opening, or higher on the wall to carve a window opening. Release commits the entire cut as one undoable edit. The chisel uses the existing draft blocks and needs no selected palette material. It removes cells from every overlapping object and any override at those positions, so older layers do not reappear in the opening. It only edits the local draft and does not demolish terrain or placed buildings. The saved document format is unchanged, including existing Door and Window object kinds; carved designs save and load through the ordinary blueprint library.

The bottom palette is two rows of compact icon buttons built by RML iteration over exported rows, with horizontal scrolling past the visible columns. Category tabs above it filter the list by the authored palette_category value, and the extra "all" tab clears the filter. Hovering a block shows its localized name in a detached design-block-tooltip above the button, outside the clipped palette scroller. The runtime reads the row's bound title as escaped text; the tooltip receives no pointer input and hides when the hover leaves the palette or the document closes. Blocks without an authored icon use a diamond placeholder. Selected blocks and the active category retain their highlighted background. The palette rows, category tabs and blueprint rows are the same kind of typed row: the engine sends arrays in building_design_state and the document renders them with data-for, so per-row structure and classes live in RML instead of markup assembled in C++. Per-row command arguments use data-attr-data-param-*, which is how each row carries its own block id, folder or file path.

The palette includes only blocks with validated construction metadata, which the registry creates for placeable: true records. Non-placeable world states, including crop growth stages, are excluded from the rows and their categories. Inventory shortage is a construction wait condition, not a palette filter. Block-selection commands use the same metadata gate, so stale UI requests cannot select excluded blocks. A previously selected block that loses eligibility resets to the first eligible block, or clears when none remain; a removed category resets to "all". Tool selection is stored by the engine and mirrored through building_design_state. Dragging edits a local sparse draft and displays translucent cell previews without modifying terrain. Select picks the frontmost draft object; delete, clear, undo and redo operate on draft history. Roof points close by clicking the first point again. Height controls and the mouse wheel adjust vertical tools. The Room tool emits a hollow ring of perimeter walls with no floor and no ceiling, so the player decides how the space is closed above and below.

Draft and drag previews are drawn as translucent real block geometry rather than abstract boxes. The engine meshes the draft through ChunkMesher per chunk and writes the result into CPU-visible vertex and index buffers that are rewritten in place, so authored block models, per-face atlas metadata and block direction match what will actually be built and no staging copy or per-frame allocation is involved. Greedy meshing merges adjacent cells of one block into a shared quad, so the draft, the selected object and the live drag preview are meshed as separate groups and keep their own tint. The ghost ignores world light. It is recorded in the SSAO geometry pass, which is where the visible scene is rasterized whenever SSAO is active, and in the single-pass path as well, because recording it in only one of the two leaves it invisible in the other. It is rebuilt at most once per frame and only when the cell signature changes, so dragging does not re-upload every frame. Only the roof polygon control points remain as debug markers.

The blueprint library, history and clipboard sections live in the right column as a plain section list and open one at a time in a fixed window slot. The blueprint window keeps the name field, the six file actions above the folder/blueprint list, and the hint and status lines below it; the history window holds undo, redo, clear and delete; the clipboard still shows its empty state until batch 3 adds copy and paste.

Start Building submits the draft through systems.building_design, which hands the cells to the ordinary block-placement pipeline so work posting, item reservation and settlement stay in one place. Only cells whose support already exists are accepted; the rest stay queued and are retried on a slow tick, so a multi-storey design fills in bottom-up. A cell that is already ordered, or that already holds the designed block, counts as resolved and leaves the draft. Cells blocked by a different block, outside the world, or without a placement definition stay in the draft and are reported, so a conflict is never dropped silently; permanent conflicts leave the retry queue so they are not re-validated on every pass. An accepted submission also closes the workspace, exactly as Exit Design does, so the player lands back in the running world with the work already ordered; a rejected press (empty or invalid draft) keeps the workspace open so it can be corrected. Re-entering the workspace later shows only the cells that are still waiting, because accepted and resolved cells left the draft. The blueprint file library keeps player-authored designs as JSON files in blueprints/, beside saves/ and logs/, and manages them entirely inside the workspace panel: no system file dialog is involved, so the library stays usable in exclusive-fullscreen and on platforms without a native dialog. Saving shifts the design so its minimum corner sits on the origin with the base plane at y = 0, orders cells, objects and overrides deterministically and renumbers object ids, which is what makes the BLAKE3-256 content id stable across sessions and edit orders, so an identical blueprint keeps one identity under any file name; cells store the block data id rather than a registry hash, so a file stays readable and diffable. The panel is a browser: its caption shows the folder being viewed, folder rows navigate into a subfolder, blueprint rows open a file and wait for its landing cell, which is stamped by clicking the ground so the blueprint's minimum corner lands there, and every row carries its own delete button that asks for a confirming second press and removes a folder together with its contents. 新建 starts an empty blueprint and keeps the discarded draft on the undo stack, 新建文件夹 creates a subfolder in the current folder, 保存 overwrites the current file, 另存 writes a new file into the folder being viewed under the name typed in the panel's name field, 重命名 renames the current file, and 返回上级 leaves the folder. The library is local player state that never travels to the Server, so every one of these commands runs on the main thread; an unplaced blueprint blocks saving and Start Building, so neither can drop it silently.

Remote clients submit through the same command. The workspace holds local engine state, so a client sends its draft cells in the command payload and the Server runs the identical submission path; the reply lists the cells the Server took over, and the client applies that list to its own draft, so both sides converge on one ghost set. The reply is handed over under its own lock and applied on the main thread, which owns the design workspace; the same handling closes the submitting client's workspace once the Server accepts the submission.

building_design.rml is a dedicated full-screen RmlUi document. The ordinary bottom bar exposes a separate Building Design button. Entering switches to the building_design UI phase, hides ordinary playing documents, and pauses simulation. Exit or Escape restores the previous pause and speed state. A paused world still services queued network commands between ticks, so a Start Building press made inside the paused workspace is handled right away instead of waiting for unpause; that is also what keeps the draft readable while the Server handles the command.

The document keeps the world viewport transparent and overlays definite-size panels. A top menu bar holds the global entries, the current blueprint name, the draft validity and the Start Building / Exit Design actions. Below it three fixed columns share the width: a percentage-clamped left rail (tool set above, tool options and draft material totals below), a flexible centre that keeps the world clickable and holds the block library at its bottom, and a percentage-clamped right column with the selection summary and the section list. Column widths are percentages with min/max clamps so the same document scales from 1280x720 to 1920x1080 without a responsive reflow; thin bars stay in pixels and every mixed box uses box-sizing: border-box. The right column opens one section at a time (blueprint library, history, clipboard) in a fixed window slot that overlays the world; dragging those windows is batch 3 work. Panel containers keep pointer-events: none so clicks between them reach the game, the ordinary HUD remains visible so its existing clock and simulation-speed controls stay in their normal location, and the design document does not create a second speed control. Its root fills the RmlUi context and uses the Unicode font family. Every visible label is supplied by the shared ui_text localization model.

The page consumes only explicitly bound fields. building_design_state is a single JSON string, so a field that is produced but not stored, read and registered as a binding renders as an unresolved variable. The blueprint library fields (design_file_name, design_file_status, design_folder_path, design_folder_parent, design_file_hint) and the section labels are bound on that chain, and the list payloads travel as arrays: design_palette_blocks, design_palette_categories, design_file_folders, design_file_entries and design_materials. Draft validity and the material totals come from the compiled design (valid, errors, materials) instead of the fixed -- placeholders the page used to print. Panel visibility is engine state bound as design_open_panel so it survives a snapshot refresh, and the toggle target is core:building_design.panel; the palette filter is engine state as well, changed through core:building_design.category.
