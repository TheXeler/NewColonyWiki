MOD 是怎样加载的

一个 MOD 就是一套数据文件加一个可选的 Lua 脚本。游戏先找到 MOD、排序、注册数据，最后跑脚本。搞清楚这个过程，后面加物品、写配方、写 Lua 才知道每样东西在哪个阶段生效。

一个 MOD 至少需要什么

游戏在 MOD 目录下找 mod.json。找到了就读取这个文件、检查依赖、排好加载顺序，然后递归扫描 data/ 下所有受支持的类型目录。入口脚本默认指向 scripts/bootstrap.lua，也可以在 mod.json 的 entry 字段改成别的路径。

下面是一个典型 MOD 的目录结构。游戏会检查 data/ 下是否存在这些类型子目录，存在就走进去递归扫描 JSON 文件。

mods/my_mod/
  mod.json
  scripts/
    bootstrap.lua
  data/
    blocks/
    entities/
    recipes/
    professions/
    civilizations/
    focuses/
    factions/
    name_pools/
    actions/
    crops/
    biomes/

加载流程

游戏启动时按下面五个阶段加载 MOD：

  1. 发现 MOD。引擎扫描 mods/ 下的每个子目录，只要目录里有 mod.json 就认为是一个 MOD。读出来之后，检查 id 是否重复、JSON 格式是否合法。
  2. 解析加载顺序。引擎按照 dependencies、load_after、load_before 三个字段计算最终顺序。循环依赖会直接报错，然后跳过出问题的 MOD。
  3. 注册数据。引擎递归扫描 data/blocks、data/entities、data/recipes 等所有受支持目录，把每条 JSON 记录放进数据注册表。注意，这时 Lua 脚本还没执行——数据在脚本执行前就已经可用了。
  4. 校验引用。配方里的输入输出、职业要求、文明开局物品、方块掉落里的引用 ID，都会被检查是否存在。如果有失效引用，引擎会报出明确的 MOD 名称和文件路径。
  5. 执行入口脚本。所有数据注册完毕后，引擎按加载顺序执行每个 MOD 的入口脚本。脚本返回一个表，引擎会读取 on_load、on_world_init、on_tick、on_shutdown 这些函数。

什么时候写 JSON，什么时候写 Lua

能用 JSON 写的东西，都放在 data/ 下。包括方块、实体、配方、职业、文明、焦点、NPC 阵营、名称池、动作（actions）和作物（crops）。Lua 只用来补充 JSON 做不到的事情：监听事件、注册焦点条件、定时执行逻辑、生成实体、操作地形。

不要在 Lua 里重新发明配方系统。新配方放在 data/recipes 下。也不要在 on_tick 里每帧扫描所有实体——用事件订阅和定时器代替轮询。

数据 ID 命名习惯

公共数据的 ID 统一用 <mod_id>:<name> 格式，例如 copper_age:copper_ingot。这样做的好处是：其他 MOD 引用时一眼能看出数据来源，也不会和 core 或者其他 MOD 撞名。

核心数据 vs MOD 数据

CoreMod/data/ 和 Examples/mods/copper_age/data/ 下的 JSON 是同一种格式，区别只在于 id 的前缀。CoreMod 内容的前缀是 core:，MOD 数据的前缀是 <mod_id>:。跨 MOD 引用时必须写完整的 mod_id:name。

如果你在 MOD 里用 dofile 加载了其他 Lua 文件（如 worldgen 脚本），注意 package 库默认未加载，请用 dofile 代替 require。
