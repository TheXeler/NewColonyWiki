外交系统本体

2026-10-11：外交使用 Server 权威谈判、Lua 提议实现和 RmlUI 界面。城邦 AI 的生成、经营、发展及回应算法另行接入；没有临时自动接受或拒绝规则。新增源码和测试源码尚未编译或运行。

独立状态与数据来源

城邦用实例 UUID 标识；关系值、战争状态、条约和玩家与派系关系分别保存。开战、议和不隐式修改关系，也不改变原有战斗敌对判断。按本轮裁定，战争不限制贸易许可的签订或使用；已有许可不因开战被撤销或停用，双方可同意一边战争、一边贸易。此裁定覆盖策划文档的贸易许可非战争前置条件。

策划列出的资源、人口、军力等是查询能力，不要求重复保存字段。Server 可用 require("core:systems.diplomacy").register_metric(id, provider) 注册数据来源，再调用 query(colony_uuid, metric_id, parameters)。未注册的指标返回 nil, "diplomacy_metric_unavailable"，不会伪装为零。内置 core:available_item_count 接受 {item_id="core:stone"}，累加 engine.items.colony_sources 的未预约数量；它不代表包括背包、所有地面物品和已预约内容在内的总资产。其他统计口径等待各系统确定。

Lua 注册

依赖 core 的 Mod 可在 Server 的 core:mod_ready 监听器中导入公共模块；不要在模块顶层访问尚未建立的世界状态。提议通过代码注册，无需 JSON 提议表。

local diplomacy = require("core:systems.diplomacy")
diplomacy.register("example:proposal", {
    name = "ui.example:proposal.name",
    forced = false,
    validate = function(context, parameters)
        return true -- or false, stable_error_code
    end,
    score = function(context, parameters) return 0 end,
    execute = function(context, parameters)
        return true -- effect applied, or false, stable_error_code
    end,
})

context 含 initiator_uuid、target_uuid、双方 relation 和外交 status。参数与 context 是副本。validate/score 必须只读，execute 在 Server 提交效果；回调不序列化，不自动换算物资价值。重复 ID 拒绝注册，运行时重载需重新注册。积分是基础诉求与所有附加条件评分之和，只用于展示和后续 AI 判断。

CoreMod 在 systems.diplomacy_proposals 中注册 core:declare_war、core:make_peace、core:trade_permission。开战是强制提议，合法提交直接执行，不等待回应；议和和贸易许可等待对方。议和暂为零分，贸易许可为 min(relation - 35, 0)。资源支付、实际贸易交付和 AI 接受决策尚未注册。

谈判接口与状态

local result = diplomacy.begin(first_uuid, second_uuid, proposal_id, parameters, conditions)
local preview = diplomacy.preview(first_uuid, second_uuid, proposal_id, parameters, conditions)
local row = diplomacy.get(negotiation_uuid)
local rows = diplomacy.list()
diplomacy.counter(negotiation_uuid, actor_uuid, expected_version, conditions)
diplomacy.accept(negotiation_uuid, actor_uuid, expected_version)
diplomacy.reject(negotiation_uuid, actor_uuid, expected_version)

每条 condition 是 {proposal_id, parameters={...}}，其 ID 也通过同一 register 注册。基础诉求保存在 base，反议只能替换 conditions，不能移除或修改 base。参数只允许可序列化普通数据，conditions 是最多 64 项的连续数组。强制提议不接受附加条件，也不能作为其他谈判的附加条件。发起者提交表示同意本版内容；反议将版本加一并把回应权交回对方。接受需要当前版本、正确回应者和仍成立的前置条件；拒绝也可用于发起者撤回。两位玩家可以在负积分时同意，框架不根据积分自动回应 AI。

操作返回 {ok=true,data=record} 或 {ok=false,error=code}；preview 返回 ok、score、forced、context。正常生命周期是 pending / countered → accepted 或 rejected。效果执行前记录 applying；作者回调失败记录 failed，不重试同一谈判。任意 Lua 副作用没有通用回滚承诺，作者应先验证并使用适当的原生结算入口。恢复遇到 applying 会标记 failed，避免重放。

服务端命令与界面

core:diplomacy.begin 携带 actor_uuid、target_uuid、proposal_id、可选 parameters/conditions。accept、reject 携带 actor_uuid、negotiation_uuid、version；counter 另携带 conditions。四条命令均使用现有 play 权限、可取消 before_event、Server 路由和 CommandResult。Server 核对 actor_uuid 与传输层绑定的城邦，不信任客户端选择。

外交列表可选择本方城邦；仅一个玩家城邦时自动选择。界面显示当前双方关系、状态、条约、提议积分、谈判诉求和条件，提供接受、拒绝、反议与条件增删。客户端作者可通过公共 core:ui.diplomacy.edit_conditions(uuid, version, conditions) 提供带参数的条件编辑器；内置界面只提供无参数的条件选择，不虚构物资支付编辑器。战略地图保留当前入口，也可进入玩家城邦的外交。

保存、同步与后续 AI

战争和条约复用 factions.json 的 pair_relations；谈判通过公共模块的 @State diplomacy 世界状态自动保存。core:diplomacy 共享状态含 factions、definitions、proposals、negotiations、perspectives 和 world_id。perspectives 为每个玩家城邦提供其与其他城邦的关系、状态、条约及提议预览，不把旧的全局玩家关系套用到联机双方。旧 C++/JSON 提议 schema 保留兼容读取，旧 evaluate_proposal 等占位接口不负责新谈判。

加载与热重载恢复会检查谈判身份和结构。缺少 Lua 提议实现时保留事实、显示 unavailable_reason，并拒绝执行；重新注册后可重新评估。Client 不保存或执行 Server 回调，断线／卸载清空显示缓存。新增 城邦算法底座以 city_diplomacy 接入同一 begin/preview/list/accept/counter/reject，并保存冷静与保护时点；正式城邦政策和全城实体桥仍未完成。战争、敌对与贸易的独立语义不变。
