职业注册

data/jobs/ 中的每个 JSON 表示职业树的一个节点。运行时身份为“节点数据 ID + 稳定职业 ID + RANK + 节点内 LEVEL”。

JSON 格式

{
  "id": "core:carpenter_3",
  "career_id": "carpenter",
  "rank": 3,
  "name": "学徒木匠",
  "parent": "core:crafter_2",
  "max_level": 5,
  "prerequisites": [
    { "id": "core:crafter_2", "level": 5 }
  ],
  "unlocks_recipes": [],
  "allowed_task_tags": ["craft"],
  "level_abilities": [
    { "id": "core:carpenter_3_level_1", "source_text": "配方解锁 I：解锁基础制作配方。" },
    { "id": "core:carpenter_3_level_2", "source_text": "制作速度 I：提升制作速度。" },
    { "id": "core:carpenter_3_level_3", "source_text": "配方解锁 II：解锁进阶制作配方。" },
    { "id": "core:carpenter_3_level_4", "source_text": "工作精度 I：提升工作精度。" },
    { "id": "core:carpenter_3_level_5", "source_text": "配方解锁 III：解锁分支职业相关配方。" }
  ]
}

字段

字段要求说明
id必填数据 ID职业树节点的唯一工程身份，例如 core:worker_2。
career_id必填文档稳定职业 ID，仅允许小写字母、数字和下划线，例如 worker。
name、description、category可选字符串字段存在但类型错误时拒绝整个职业定义，不将其静默视为缺省。
rank必填，1-5职业树 RANK。相同 career_id + rank 不可重复。
max_level0-5节点内 LEVEL 上限；零级节点没有等级天赋，也不生成正等级资格表达式。Task 资格由职业定义及其继承的允许标签决定，不查询当前装备。CoreMod 的初始 colonist 节点是零级实例，其他 Mod 可声明自己的零级节点。
parent可选节点 ID职业树父节点，也是当前职业能力和职业 tag 的继承链。旧字段 tree_parent 会被拒绝。
prerequisites可选数组转职必须全部满足的前置节点和 LEVEL；交叉职业据此保留两条前置链。inherited_nodes、career_tags、能力的 modifiers 也是可选数组；这些字段存在但类型错误时拒绝定义。
unlocks_recipes可选数组字段存在时必须是数组。非空项可写配方 ID 字符串（默认 1 级），或写 {"id":"mod:recipe","level":N}；对象省略 level 时也默认为 1。空 ID、显式错误的等级类型或超出 1-5 的等级会拒绝定义。
allowed_task_tags可选数组当前节点可执行的 Task 标签。旧字段 allowed_task_types、allowed_job_types 会被拒绝；字段存在时必须是数组。需求、基础急救等文档基础行为另行处理。
level_abilities项数等于 max_level依次对应节点的各级能力；零级节点使用空数组。每项必须有非空且在全部职业中唯一的稳定 id，以及文档原文 source_text；空 ID 或重复 ID 会拒绝职业定义集合。只有文档明确给数值时才写 modifiers。
modifiers[].stat属性完整路径使用统一属性键，例如 colonist.work_efficiency、battler.melee_hit 或 ECS 引擎字段 max_hp。包装层按键选择 Map 或 ECS 基础值；修正值接受 JSON 整数或小数，必须有限且可表示为引擎 f32。
modifiers[].modeadd 或 base_percent职业定义加载时拒绝其他模式，也拒绝把 position、velocity、rotation 父节点或字符串 name 用作数值修正目标。
level_abilities[].capabilities属性声明数组支持与实体相同的 pack 引用及标量声明。C++ 校验并展开声明，同时向 Lua 提供原始声明；Lua 选出生效天赋后按原始声明批量安装 pack，使覆盖值和嵌套 pack 一次展开，已有同来源能力的当前值不会被再次同步覆盖。缺失的独立标量逐键新增，缺失的 pack 子节点不会被当作另一份 pack 静默重建。职业进度由 C++ 提交，随后由 Lua 同步玩法效果；同步失败报告错误，不回滚已提交的职业变更。民兵与魔法师首个天赋声明 battler pack；战士、骑手和战斗医兵经民兵前置继承，魔法师 3 至 5 阶节点声明为战斗职业。玩家征召 Lua 命令核对当前 Job 的战斗类别和解析后的 battler 能力。

职业资格表达式

工作实例保存由职业 tag、AND、OR 和括号组成的表达式。tag 格式为 #职业ID_RANK_LEVEL，例如 #worker_2_5。

  • tag 是最低门槛；同职业线中更高 RANK 或同 RANK 更高 LEVEL 可以满足。
  • 只读取当前装备对应节点及其父节点/前置链；已解锁但不在当前链中的履历不参与。
  • 交叉节点读取其全部前置链，不套用额外的固定组内或组间规则。
  • 旧 required_job_id + required_job_level 只在读档时转换成表达式，新工作不再写入它们。
(#militia_2_5 AND #apothecary_2_5) OR #combat_medic_3_1

初始殖民者由 core:colonist 原型生成，保持该职业的无等级状态（Job.level=0）。招募候选人另有 PendingRegistration 标记；单凭 0 级不会把正式殖民者识别为候选人。

能力与履历

当前节点只应用已达到 LEVEL 的能力；父节点和交叉前置节点按满级继承。切换职业后，普通能力不生效；只有数据中明确标为 permanent 或 cross_career 的能力可从独立履历继续生效。CoreMod 当前能力文本直接来自 NCDOCS，未定义数值的“提升”不会被引擎猜成倍率。

经验提交导致等级变化时，C++ 发布 core:job_level_changed，CoreMod 的 Lua 监听器同步新等级天赋；原生 AI 迭代产生的事件在迭代结束后投送。职业定义热重载保留原生等级变化回调，后续升级仍会通知 Lua。转职由 core:job_assigned 同步。普通 task_completed 不再为职业效果执行第二次同步；监听器错误由事件系统记录。若通知投送本身失败，原生记录 ERROR，已经提交的经验或转职仍向调用方报告成功；职业能力可能暂时滞后，后续读档或 Mod 重载会重新同步，不自动重试本次事件。

没有职业定义的原型实体仍有空 Job 组件，初始职业 ID 为 0。空 Job 属于 Job，可以执行基础和生存 Task；具有 ColonistTag 的空 Job 实体也可以接取用于取得职业的 JobChange。缺少 Job 或 ColonistTag 的实体不能接取 JobChange，与转职提交条件一致。转职 Task 的目标是装备所在方块库存，导航会选择该方块邻近的可站立位置。engine.jobs.transition_state(entity) 对空职业返回 current_job_id=0、current_level=0、career_count=0 和空的 levels/history 表。Lua 资格回调若接受其转职，C++ 只把目标职业写入履历；空职业 ID 不会被记录为历史节点。

读档遇到未注册的职业 ID 时，引擎记录含该 ID 的 ERROR，并保留当前职业及履历中的原始 ID、等级、阶级和经验。后续存档继续保存这些值，重新启用缺失的 Mod 后仍可恢复职业定义。

Lua/UI 接口

API说明
engine.jobs.defs()返回节点 ID、career_id、rank、前置、工作 tag 和五级能力。
engine.jobs.tree()按 RANK、排序值和节点 ID 返回职业树。
engine.jobs.can_transition_reason(entity, node_id, source)检查当前实体的职业前置及方块库存来源；C++ 将候选物品 ID 交给 Lua 转职回调，由 CoreMod 检查 equipment 与 supported_jobs。提交时会按预约中的物品再次调用同一回调；commit_transition 返回成功标志和失败原因，再由 C++ 交换装备并记录职业状态。
engine.jobs.progression_configuration()返回职业经验配置屏障；内容表为空时不会生成经验默认值。
engine.tasks.set_qualification_expression(task_id, expression)给工作保存权威资格表达式。

CoreMod 当前状态

CoreMod 注册文档规定的 66 个职业节点。职业装备内容尚未声明时，转职入口保留并显示装备配置缺口，不把旧工具方块猜作许可装备。战斗职业只保留职业、属性和装备接口；战斗专项规则仍未定义。
