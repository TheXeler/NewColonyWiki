Lua 怎么用

Lua 入口用来连接事件、定时器、要闻、实体和地形扩展。能用 JSON 的内容仍然优先写 JSON。

脚本运行时：LuaJIT 2.1（Lua 5.1 语言）。不要使用 5.3+ 才有的位运算符（& | ~ << >>）和整除运算符 //——需要位运算时改用 bit 库（bit.band、bit.bor、bit.bxor、bit.lshift、bit.rshift）。注意 bit 库只在 32 位上运算。
MOD API 版本：当前公共脚本 API 版本可读 engine.api_version，也可读 engine.version.api。
API 稳定性：速查页按 stable 和 experimental 标记接口。稳定接口用于普通内容 MOD 和 CoreMod 路径；实验接口通常是低级 ECS、世界修改、网络命令、编辑器或运行时注册能力，可用但后续可能收窄权限。
沙箱边界：MOD Lua 不暴露进程和通用文件系统能力。os、io、debug、dofile、loadfile、load、loadstring 不可用；package.loadlib、package.path 和 package.cpath 也不可用。加载同 MOD 下的预编译 Lua 模块请使用 require。少数内容文件入口（例如语言包加载和蓝图导入）限制在 MOD 或 generated 内容目录内。

入口脚本结构

mod.json 里的 entry 指向入口脚本。脚本运行后返回一个表，引擎读取表里的生命周期函数。不需要实现全部四个——只写你需要的即可。

local M = {}

function M.on_load()
  engine.log.info("[copper_age] data loaded")
end

function M.on_world_init()
  engine.log.info("[copper_age] world is ready")
end

function M.on_tick(tick, dt)
end

function M.on_shutdown()
  engine.log.info("[copper_age] shutdown")
end

return M

四个生命周期函数的用途：

  • on_load —— 适合订阅事件、注册要闻条件、读取配置和恢复非世界领域状态。此时数据与完整领域 API 已绑定，但世界还没生成。
  • on_world_init —— 适合生成世界相关内容、初始实体、注册 terrain biome/ore/feature。此时地形 API 已可用。
  • on_tick(tick, dt) —— 每帧执行。这个地方的逻辑要尽量轻，不要在每帧做大规模扫描。
  • on_shutdown —— 清理工作，比如写日志。

日志和配置

读取 MOD 配置时记得给第三个参数 fallback，避免旧配置缺字段时报错。

local debug_logs = engine.modding.get_setting("copper_age", "enable_debug_logs", false)

if debug_logs then
  engine.log.info("[copper_age] debug logging enabled")
end

读取和操作实体

不提供通用实体创建、任意销毁或逐项写入生命、需求、心情、AI、交互意图、原型身份和装备组件的低级入口。物品、殖民者、生产、掉落、治疗和招募必须经过各自的 Host 权威事务；生态系统只能用已注册 animal_distributions 规则 ID 生成对应动物。引擎定义的物理属性可通过 engine.ecs.get_gravity_enabled(entity) 和 engine.ecs.get_collision_enabled(entity) 查询，并由 Host 权威脚本调用对应的 set_gravity_enabled、set_collision_enabled 动态修改。

local id = (engine.ecs.query_with_health() or {})[1]
if not id then return end
local hp = engine.ecs.get_health(id)
engine.log.info("health: " .. tostring(hp.current) .. "/" .. tostring(hp.max))

实体附加数据

实体上的"键 → 带种类的值"数据表，用于任务状态、临时标记或脚本私有计数。键是数据 ID，种类由引擎决定（bool / int / float / string / uuid / vec3 / enum），并且会随存档保存、随网络同步。

宿主对象只能从事件回调里得到：任何携带实体的事件都会在负载里给出 host（施动实体，entity_id 优先、其次 worker）与 target_host（工作目标实体）。宿主是句柄而不是普通表——实体销毁后再调用会立刻失败，不会写到被复用的实体 ID 上。

engine.events.subscribe("work:completed", function(event)
    local host = event.host
    if not host or not host.valid then return end
    local map = host.attachmentsMap
    if not map:has("core:harvest_count") then
        map:attach("core:harvest_count", 0)  -- 建键：有声明按声明种类，无声明按 Lua 类型推断
    end
    map:set("core:harvest_count", (map:get("core:harvest_count") or 0) + 1)
    for key, value in pairs(map:list()) do
        -- 遍历该实体当前附着的全部键值（UI 用）
    end
end)

attach 建键、set 只改已存在的键（键不存在会报错）、get 缺键返回 nil、has 判存在、detach 移除、kind 返回该键的种类名、list 返回全部键值。同一个键不能改种类：跨类覆盖是致命错误。写操作只在主机侧放行，客户端只读。

可用键写在各持有者定义的 attachments 数组里（实体原型、物品定义、方块定义各自声明），缺省值在生成实体时写入；运行期也可以附加未声明的键，但那样种类只能从 Lua 值推断（表值不接受）。例如在实体原型里：

"attachments": [
    { "id": "yourmod:battery", "type": "float", "default": 1.0 },
    { "id": "yourmod:mode",    "type": "enum",  "values": ["idle", "patrol"], "default": "idle" },
    { "id": "yourmod:home",    "type": "vec3",  "default": [0, 64, 0] }
]

这样生成的每个该原型实体，一开始就带着这三个键与默认值；之后用 host.attachmentsMap 读写即可，存档与网络同步都由引擎处理。引擎保留键（health、position 等）的声明写法尚未定案（见附加数据设计文档与搁置问题清单的 D5），本示例只用自定义键。

键名规则（写内容前务必确认）：引擎保留键用裸名（health、position、rotation…，完整清单见附加数据设计文档 §3.2）；你声明的其他键如果不带命名空间，会被自动补上你的模组名（work_precision → 你的模组:work_precision）。所以自建键请始终写成 你的模组:键名，避免与别的模组撞名。键名只允许小写字母、数字、下划线、短横线和命名空间冒号。

声明的取值形状：每个声明的 type 决定取值形式——bool 为真假值；int / float 为数字（两者不可互换，写 1 与 1.0 会按声明区分）；string 为字符串；uuid 为 32 位十六进制字符串（可带连字符）；vec3 为 [x, y, z] 三元数组；enum 必须额外给 values 取值表，且默认值与附加的值都必须是其中之一。任何声明都必须写 default。

同一个键不能改种类：无论是声明还是运行期附加，一个键一旦以某种种类存在，再用另一种种类覆盖都是致命错误（游戏会终止并先刷新日志）；同一键被多个定义声明时，类型必须一致。

物品也有同样的表。物品事件（item:spoiled、item:ground_despawned）的回调里给的是 event.item，接口与 host.attachmentsMap 完全一致（attach / set / get / has / detach / list / kind / valid），读写的正是该物品实例的附加数据。

与实体不同的是失效时的表现：实体宿主在实体消失后根本不会交给你（字段为 nil），而物品句柄可能拿到，但每个操作都会像"键不存在"那样失败（写操作返回 false）——两种做法都保证不会把数据写进已被回收的实例。

engine.events.subscribe("item:ground_despawned", function(event)
    local item = event.item
    if not item or not item:valid() then return end
    if item:has("yourmod:freshness") then
        item:set("yourmod:freshness", 0.0)
    end
end)

物品附加数据与实体一样随存档往返、随网络同步，并参与同类物品的堆叠合并判定（附加数据不同的两堆不会合并）。物品定义里同样可以写 attachments 数组来声明键与默认值。

方块也有同样的表。凡是负载里带数值 x／y／z 的事件都会给出 event.block——包括 block:interacted／block:removed／block:changed／block:placed，也包括 work:*（那里的坐标就是被施工的方块）。接口与另外两个宿主一致。

engine.events.subscribe("block:interacted", function(event)
    local block = event.block
    if not block or not block:valid() then return end
    block:attach("yourmod:tended_at", event.tick or 0)
end)

方块的失效表现与物品类似但原因不同：坐标不存在"存活"一说，**区块没加载时你仍会拿到句柄，但每次操作都返回失败**；并且引擎**不会为了读而创建区块**。请注意：方块附加数据目前只存在内存里——实体与物品的附加数据会随存档往返、随网络同步，方块的要等后续阶段（设计文档 §4.5 的 V3/V4）才接上，当前卸载区块即丢失。

旧的 engine.data 数据组件 API 与本节重叠，且不存档、不同步、实体销毁不清理，已随本 API 一起删除（该 API 与旧 wiki 页均已移除，导航项也已去掉）；它的点分路径与表值请改为多个扁平键。旧说明见 数据组件 API（待重写）。

合成和职业

配方和职业本体写在 JSON 里。公开直通制作和职业分配入口均已禁用；Lua 可以查询配方，并通过 CoreMod 生产订单和装备换装事务创建实际工作。

for _, recipe_id in ipairs(engine.crafting.list_recipes()) do
  local recipe = engine.crafting.get_recipe(recipe_id)
  if recipe then
    engine.log.info("recipe: " .. recipe.id .. " -> " .. recipe.output.id)
  end
end

CoreMod 菜单通过 systems.production.queue 建立可重复或维持库存的订单，再由 systems.crafting.queue 预留 stockpile 材料并在 work:completed 后结算；Lua 不提供直接制作入口。

engine.designs.attribute_ids() 返回只读且有序的引擎属性名表（26 项，索引 1..26），顺序与 Engine/Simulation/AttributeStats.hpp 一致。物品基型的 base_values 键、attributes[].id 以及品质表的 modifiers[].attribute 都取这份名单，表外名字在配置期被拒绝。编辑器与工具应以该入口生成属性下拉，不要再各自硬编码副本。

engine.designs 提供锻造基型和不可变设计方案接口。list_item_bases()/get_item_base(id, civilization_index?) 返回基型、科技解锁状态、属性/词条等级、容量、材料与配置错误；preview(base, attributes, affixes) 只计算方案；save(...) 仅允许已解锁基型并始终创建新 design ID，即使方案因容量或选择错误而无效。list()/get(id) 返回已保存方案。方案没有名称或批量数量字段。

工作池

发布工作时必须指定工作所属阵营。faction_id 使用数据 ID 哈希，玩家/殖民地工作通常使用 core:player。AI 只会领取与自己阵营一致的工作。

工作系统内部有 WorkTag、WorkCategory、WorkTargetKind、WorkAction 和 WorkPayloadKind，但当前 Lua 只公开发布工作实例的兼容入口，没有公开的工作类型注册 API。

engine.work.post(type, faction_id, x, y, z, duration, payload_id, target_entity) 中的 type 支持 build/construction/plant、repair、mine_operation、haul、craft/manufacture/cook、use_medicine/medicine/use_potion、transfer_patient/carry_patient、job_change/change_class、treat/treatment/heal、feed_patient/patient_feed、first_aid/stabilize、battlefield_treat/medical_pack、guard 和 patrol。未知类型、缺失或非正数 duration 固定返回 0。target_entity 是可选实体目标；非零 payload_id 作为 Custom payload 保存。一次性 Mine/Chop 只能由指定工具确认后经 Host 命令创建；研究工作只由 engine.research.begin 已成功开启且支付材料的研究项目派生。通用 engine.work.post 不接受这三类来源工作。

local player_faction = engine.util.data_id_hash("core:player")
local work_id = engine.work.post("haul", player_faction, 16.5, 65.0, 16.5, 3.0, 0)

底层执行不再查找数据驱动 action 注册表。引擎根据目标类型、Interact/Destroy、工作标签和 payload 语义处理方块交互、规划方块放置、实体攻击或脚本事件。

订单元数据可用 engine.work.set_metadata(work_id, source_id, priority, designated_worker?) 写入；普通优先级范围为 1-9，0 保留为特殊优先级。engine.work.set_qualification 可要求指定职业和等级。需要物品的工作还必须调用 engine.work.set_item_requirements(work_id, rows) 声明领取时材料资格；每行使用 count 加具体 instance_id，或 item_id/candidates 候选集合。同一实例数量会在整组要求间统一核算，领取只检查当前玩家仓储中可达、启用、未保留且未预留的数量，不提前占有；真正的 reserve/reserve_instance 仍只在 work:activated 后执行。set_available/available/reserved/reserve/commit_reservation/release_reservation 暴露共享资源预留账本。

公共工作先进入殖民者个人队列，领取本身不触发预留。领取初选和未激活队列继续执行共用职业、工作计划、状态、路径与当前材料可满足性条件。调度器每轮按稳定殖民者顺序让每名空闲且合格的殖民者至多认领一项；后一名殖民者只会从前者尚未认领的工作中选择，因此优先形成 A、B、C 的均匀分配，不再先填满某一人的队列。个人队列上限仍为 20 项。AI 每 5 tick（250 ms）检查一次公共池，已有个人工作时不会补领或被更高优先级工作抢占。

队列中的一项真正激活后才触发 work:activated，制作等经营系统在此时申请资源和位置预留。激活检查失败时可调用 engine.work.activation_failed(work_id)，它会把该项退回公共池、清理导航并阻塞 20 tick；执行者随后尝试队列下一项。engine.work.set_locked(work_id, true) 复用同一个 blocked_until_tick 字段写入永久阻塞哨兵，任务继续存在但不能被领取；传入 false 会把阻塞时间恢复到当前 tick 并立即解锁。完成结算与下一项激活分属不同 tick，避免下一项在上一项提交前抢先预留。

取消和中断分别触发 work:cancelled 与 work:interrupted。engine.work.interrupt_all(worker) 会把当前激活项和整条个人队列全部退回，释放激活项未提交预留；其他殖民者可立即领取，原殖民者在 20 tick 内跳过这些工作。

搬运是唯一允许同批多项同时激活的类型。CoreMod 只合并来源坐标、物品堆叠键、来源位置和目标仓储位置都兼容的项，并按背包格、单格堆叠与搬运容量截断。engine.work.claimed(worker) 提供该人尚未激活的队列，engine.work.personal_load(worker) 与 engine.work.personal_limit() 给出个人队列的加权负载与上限（摧毁/放置体素类工作每项占 1 格、其他类型每项占 10 格，总上限 20；人员界面的“当前工作数量”即显示该负载），engine.work.activate_claimed_haul(work_id, worker) 只允许激活其中的 Haul 项；各项仍独立保存来源、数量、目标格和预留，并由 AI 逐项导航结算。合成系统在成功创建每个产物实例后立即调用搬运系统的幂等入库入口发布 Haul 工作，周期扫描仅作为遗漏恢复。没有有效仓储目的地时自动搬运任务仍会发布，但使用永久冷却哨兵锁定；目的地出现后自动解锁。拆分物品堆时，原始来源实例会保持占用到当前批次交付完成，防止携带者被同一堆的新取货任务抢走；交付结算后立即扫描剩余来源并发布下一批，不等待周期扫描。

寻路失败会被记为 error；AI 不再因导航目标不可达而生成原地 fallback 工作。

如果 AI 在执行中被中断（例如殖民者倒地、死亡、低需求触发个人需求，或 AI 状态被外部清空），当前激活项和未激活个人队列都会返回工作池；只有激活项可能持有预留。恍惚只影响命中率，不会单独中断工作。

engine.economy_log.record(spec) 向统一经营日志追加结构化正常/异常记录；engine.economy_log.entries(filter?) 只读查询并支持 worker、source_id、source_object_id、item_id、work_tag 和 problem_id 筛选。engine.problems.report(spec) 按来源与问题 ID 上报或刷新持续问题，list(filter?)/alerts() 返回局部问题和同类聚合警报，resolve(instance_id) 解除并自动写日志。个人进食工作按殖民者保持唯一；暂时找不到或无法预留食物时只冷却并重试同一工作，不记录逐次激活失败，也不上报普通缺粮问题。殖民者进入会持续损失生命的严重饥饿阶段后，才产生按人数聚合的全局持续警报。问题 API 只表达文档已有的阻塞/失效反馈，不应创建新的玩法规则。

systems.work_policy 保存工作计划和排班模板、殖民者分配及个体覆盖。六个工作计划开关依次为搬运、建造、维修、制作、采集、职业；排班的 24 个小时槽取值为 0=睡眠、1=工作、2=自由。工作时段可领取普通工作，自由时段只领取特级工作并允许社交/娱乐，睡眠时段不领取普通工作；进食、休息、逃跑、紧急急救和即时威胁响应不受这些开关限制。模板修改会重新计算全部使用者的有效策略。没有工作策略组件或尚未配置六类开关时，普通工作固定拒绝；网络实体载荷也不提供全开启缺省值。

engine.colonists.work_policy(entity) 返回有效开关、小时表、模板 ID 和覆盖掩码；engine.colonists.set_work_policy(entity, spec) 是模板系统写入有效状态的低级接口。玩家界面通过 work_policy_state 快照及 core:work_plan.*、core:schedule.*、core:work_policy.* 命令管理模板，不直接修改 AI 内部类别优先级。

事件

订阅事件时保存返回的 handler id，之后可以取消订阅。优先用事件响应具体变化，不要在 on_tick 里反复扫描所有实体。

local handler = engine.events.subscribe("inventory:changed", function(evt)
  if evt.item_key == "copper_age:copper_ingot" then
    engine.log.info("copper ingot changed by " .. tostring(evt.delta))
  end
end, 10)

engine.events.unsubscribe("inventory:changed", handler)

常用引擎事件如下；CoreMod 游戏系统还会发出 stockpile、production、treatment 等自定义事件：

事件名payload 字段
inventory:changedentity_id, reason, item_id, item_key, delta
recipe:craftedentity_id, recipe_id, output_item_id, output_item_key, output_count
job:assignedentity_id, job_id, level
block:interactedentity_id, x, y, z, action_type, action
work:completedinstance_id, worker, tag, category, target_kind, action, payload_kind, payload_id, faction_id, x, y, z, target_entity, tick
work:cancelled / work:interruptedinstance_id, worker, tag, payload_id, faction_id, source_id, tick
colonist:deathentity_id, name, tick, x, y, z；死亡实体随后会被销毁，并可通过 engine.colonists.memorials() 查询纪念记录。
focus:chosenfocus_id, instance_id, choice_id, choice_action, tick
focus:dismissedfocus_id, instance_id, tick

也可以用 engine.events.emit("core", "name", payload) 发送自定义 Lua 事件；来源必须放在事件名前面。

装备系统

装备组件只有一个固定槽位：Equipment。Lua API 使用 equipment.item 表示当前装备，不支持旧的主手、副手、护甲、饰品槽，也没有双手占槽规则。

-- 将玩家仓储中的具体实例换入唯一装备槽
engine.ui.command.run("core:colonists.change_equipment", { entity_id = entity_id, instance_id = instance_id })

-- 已进入职业后不能单独卸装；这里只读取当前装备
local current = engine.equipment.get_slot(entity_id, "Equipment")
engine.log.info("current item: " .. tostring(current.item_id))

-- 查询实体所有栏位
local eq = engine.equipment.get_equipment(entity_id)
engine.log.info("equipment: " .. tostring(eq.Equipment.item_id))

-- 查询单个栏位
local held = engine.equipment.get_slot(entity_id, "Equipment")
if held.item_id ~= 0 then

end

物品 ID 可使用 engine.util.data_id_hash("example:item") 计算稳定哈希。

统一物品与玩家仓储

engine.items 访问 C++ 权威物品实例。total/available/reserved(item_hash) 查询玩家仓储数量；只有露天仓储和储存体素会被计入。storage_snapshot() 返回按物品汇总的数量，instances() 返回带稳定 instance ID、位置、品质和载荷的实例快照。

统一资源预留排除不可达、禁用及实例/仓储保留策略，并按仓储取用优先级和路径成本选择。storage_policies、set_storage_policy 和 remove_storage_policy 管理物品/分类/标签过滤及存取优先级；储存体素策略还声明坐标、格数、最终单格容量与冷藏状态。搬运通过 reserve_storage_destination 在激活时同时锁定来源数量和目标格，到达来源后把数量移入统一背包实例，完成目标阶段时提交；中断/取消时释放。由采掘/砍伐结算产生且带 recovery_authorized 的背包物品会先生成指定原持有者、特殊优先级的入库工作，释放真实背包格后再领取地面搬运；地面搬运激活前必须存在空背包格。直接存取和直接移动仓储入口已移除，普通玩法只能通过工作和经营事务改变库存。create(table) 不是通用造物入口：它只在引擎派发真实 Craft 或 MineOperation 完成事件期间接受调用，位置必须是当前工作的 output_buffer，location_id 和 compatible_work_id 必须分别匹配当前工作点和工作 ID，所有权必须是玩家；其他调用固定返回 0。place_player_output(...) 也不是通用造物入口，只在真实 Mine/Chop 完成结算或 Host 正在处理 recruitment.cancel 退款时开放。成品可通过 payload 保存 JSON 兼容载荷。Lua 不应维护第二份 stockpile 数量表。

local item = engine.util.data_id_hash("example:item")
local available = engine.items.available(item)

engine.items.reservation_sources(item_hash) 返回 reservation ID、来源、目标及具体实例分配。engine.work.commit_reservations(rows) 会在全部预留均有效时一次性消费所有实例；任一项无效时不消费任何一项。提交后不要再次调用库存扣除。

engine.work.move_reservation_to_input(reservation_id, work_point_id, work_id) 将已预留实例送入兼容工作的无限输入暂存。engine.buildings.work_points()、work_point_status 和 find_available_work_point 提供生产所需的入口道路、内部路径、占用和输出阻塞状态。engine.manufacturing.quality_thresholds() 按全局制造规则的配置顺序返回品质阈值，生产过滤界面必须使用该顺序，不应另设硬编码品质等级表。

物品腐坏和地面消失由引擎 tick 推进。引擎发出 item:spoiled、item:ground_despawned 和 reservation:invalidated；预留物腐坏无法换绑时，来源工作会进入 20 tick 阻塞。

生存、饮食和治疗

engine.colonists.detail(entity) 返回 condition、injuries 和死亡/倒地状态；engine.colonists.survival_configuration() 返回唯一 colonist_survival_rules 记录的有效状态与稳定错误 ID，CoreMod 的 systems.survival 将无效状态登记为全局持续问题。需求消耗、状态转换、压力/崩溃/恍惚、属性倍率、状态伤害、饱食恢复和濒死均不使用代码平衡默认值。MoodSystem 只保留由事件或内容明确加入的心情印象和配置驱动的状态贡献，不再按饱食、疲劳或心情阈值生成固定数值/持续时间的内置印象，也不把心情作为未定义的职业经验倍率。进食仅可通过 engine.colonists.apply_nutrition 在匹配的 Eat 工作完成派发期间提交；急救、正式治疗、病号喂食和战场治疗只可通过 apply_treatment_result 在工作 ID、类型和患者均匹配时提交。CoreMod systems.food 管理进食方案，从 engine.items.instances() 返回的玩家露天仓储和储存体素实例中按允许/禁用物品、分类、标签、品质、腐坏、营养溢出和路径长度选择具体实例。新建和默认方案的允许过滤初始为空，不会隐式放行整个 food 分类；玩家明确配置后普通进食和治疗点喂食才会在工作激活时通过 engine.work.reserve_instance 预留，并在完成时提交。engine.navigation.path_length 返回两个世界位置之间的寻路长度；不可达时返回正无穷。systems.treatment 管理治疗模板、治疗点容量与 Treat 工作；模板按每种已启用伤病/状态分别保存食物、药品和医疗包，资源不会跨状态共享。这些状态通过 runtime_states.json 随世界存档。

engine.colonists.set_medicine_slot_capacity 是系统应用个人通用药剂 CD 槽上限的低级入口；reserve_medicine_slot、commit_medicine_slot 和 release_medicine_slot 分别对应药剂使用工作激活、成功和失败/中断。medicine_slots 返回总数、预留数、占用数、药剂物品 ID 和剩余秒数。CoreMod 从唯一 medicine_slot_rules 数据记录读取基础容量和科技增量；systems.medicine.slot_capacity_state(entity) 返回期望/实际容量、预留、占用、逐槽状态、容量来源和配置错误。CoreMod 当前基础容量为 2，状态显示在人员界面的个人信息中；记录缺失时仍保留 medicine_slot_rules_missing 屏障。

engine.json.decode(text) 在基础 Lua API 绑定阶段注册，因此 MOD 的 on_load 可以把 engine.modding.get_data_json(type, id) 返回的原始 JSON 解码为 Lua 值；空字符串或无效 JSON 返回 nil。engine.runtime_state.set(key, table) 和 get(key) 提供按稳定 key 保存 JSON 兼容 Lua 值的低级状态仓。状态仓可由异步存档线程安全快照；系统应在状态变化后写入，并在 on_world_init 中恢复。玩法领域载荷必须保存当前 schema_version = 1 并拒绝明确的未知版本；项目尚未发布，不维护旧领域结构的兼容读取。函数、userdata 和循环表不能作为持久化值。

engine.colonists.memorials() 返回死亡殖民者的实体 ID、姓名、职业、等级、死亡 tick 和位置；纪念记录会写入 world.json。建筑治疗点 API 详见建筑蓝图注册。

engine.buildings.raid_target() 返回当前袭击目标的 valid、稳定错误 ID、建筑实例/定义、角色、价值、位置和当前难度 raid_multiplier。选择顺序固定为已完成城镇大厅优先，否则最高价值玩家建筑；该接口不创建袭击，也不定义额外的袭击公式。

engine.buildings.repair_status(instance_id) 和 repair_statuses() 返回耐久、配置上限、授权、材料、职业、工作量、单元恢复量和稳定问题 ID。damage 是战斗/事故提交建筑伤害的低级接口；set_repair_authorized 是 Host 授权入口，apply_repair_unit(work_id, instance_id) 只在匹配该建筑 payload 的 Repair 工作完成派发期间结算。CoreMod systems.repair 负责 Repair 工作、激活预留、原子提交、取消释放和经营日志；玩家操作走 building.repair_authorize Host 命令及 building/repairs 数据通道。

engine.buildings.storage_points() 和 storage_point_status(id) 返回稳定位置 ID、建筑/定义、坐标、容量、冷藏、存在/可用及永久失效原因。CoreMod systems.building_storage 将可用点安装成通用 storage_voxel 策略并进入 building/storage_points 通道；损毁/拆除时通过 engine.items.drop_storage_contents 将内容转为授权地面实例，并清理关联预留。

engine.buildings.instances() 返回所有权威建筑实例的稳定 ID、定义 ID、状态和原点，供需要按完整建筑集合恢复派生索引的系统使用。CoreMod systems.world_components 维护多体素部件的稳定实例 ID、类型、定义、owner、逐格坐标/hash 和产出表引用；只读通道 world/components 返回 { schema_version, instances }。当前自然树生成是单格对象，因此首次交互只注册目标格；系统不会以相邻同类方块推断同一对象。真正的多体素生成器必须在创建时提交明确 cell 集合。

engine.terrain.ecology_chunks() 返回当前强加载区块的坐标、主群落、基础/最终温度和树木统计；engine.terrain.ecology_animals() 返回实际存活动物实体、原型、攻击性和位置。CoreMod systems.ecology 按两类生态内容表推进刷新，并通过 core:ecology 运行态保存资源点索引和逐规则/区块的下次检查 tick；snapshot()、resource_point_at(x,y,z) 和统一 ecology/state 数据通道提供只读接口。空内容表不扫描世界并报告稳定配置问题。

CoreMod systems.world_locations 保存玩家指定的唯一贸易点；world/locations 通道返回位置、是否已配置和 caravan_arrival_allowed。玩家通过 Host 命令 location.trade_point.set 在当前可站立位置设置，或用 location.trade_point.clear 清除。未设置时明确返回 trade_point_missing 并阻止商队到达接口；系统不在缺少贸易专项规则时生成商队、价格或交易结算。

engine.visibility.configuration() 返回唯一视野规则的配置状态；state_at(cx,cz) 返回 unexplored/explored/visible，chunks() 返回全部探索记忆与当前可见标记。未探索区块不提交地形渲染；已探索但不可见区块只保留地形记忆，不提交活动实体；当前可见区块显示地形和实体。待登记新人不作为视野源。探索记忆写入 world.json 并沿 save_state:world Host 通道复制。

职业等级按节点独立保存在 CareerProgress；切换职业会保存原节点等级并恢复目标节点既有等级。engine.colonists.career_tree(entity).levels 返回全部已有职业等级，equipment_options 返回目标职业当前可选择的具体玩家仓储装备实例。engine.jobs.set_career_level 只接受尚未登记且当前仍为无等级初始职业的候选人，用于一次性写入候选履历，不能修改正式殖民者职业。

待登记新人带有 PendingRegistration 状态。engine.colonists.find_recruitment_entry 遍历当前已加载区块，使用 VisibilitySystem 的真实三态视野选择距当前可见区最远且实际可寻路到大厅的位置；它不把强/半加载半径解释为玩家视野。待登记实体不扩展可见区、不领取工作、不推进生存伤害并按中立目标处理。抵达大厅后由招募系统解除该状态。

systems.potion 只从注册表读取 medicinal_herbs 与 potion_trait_effects，并由效果记录的公共区间边界构建四项独立效果表。系统另提供剂型固定材料、科技/容量许可、设计预览和保存。六种剂型倍率及 0-4 级基础 CD 由设计文档固定；药材和效果内容为空时不会生成默认条目，也不能保存无效果配置的药剂设计。configuration() 及 snapshot().configuration 返回 valid/errors/herb_count/interval_count/registered_trait_effect_count/missing_effect_ids，snapshot().trait_effects 暴露加载结果和来源路径。空表分别报告 potion_herbs_missing 和 potion_trait_intervals_missing；缺少 Lua 生命周期定义时按具体效果 ID 报告 potion_effect_definition_missing。configure_form_material(form, item_id, count, recipe_id) 将剂型关联到固定配方；秘粉的 item_id=nil/count=0，其他剂型固定材料数量必须为 1。关联配方必须使用成败模式。

已保存药剂设计通过生产订单进入兼容工作点，激活时统一预留逐味药材和剂型固定材料、送入输入暂存，完成时使用配方的标准成败/产出表并原子提交。目标剂型物品的成品载荷严格只写效果表和最终 CD，不写药材序列、计算过程或设计名称；重复效果 ID 原样保留。失败会消耗材料但不生成受制造模式影响的目标。

systems.medicine.queue(user, target, instance_id, duration, faction_id) 发布隐藏的药品使用行为。激活时通过 engine.work.reserve_instance 预留指定载荷实例，并预留目标的空药品 CD 槽；完成后消费一个实例、应用载荷效果并用载荷 final_cd 占槽。失败、中断或取消释放实例和槽，其他进食行为不受没有空槽影响。治疗模板同样按具体药剂实例读取最终 CD，不再允许模板另填 CD。NCDOCS 尚未定义用药动作本身的工作时长，因此 duration 缺失或非正数时固定返回 medicine_work_duration_undefined，不会回退到私有的 1 秒默认值；治疗、急救、病号喂食和患者转移使用同样的显式屏障。

systems.effects 通过 register_definition(effect_id, definition) 注册 instant、modifier_start、modifier_tick 和 modifier_end。每次成功用药建立独立效果组；组记录药品实例、目标、CD 槽、组内剩余时间、JSON 状态和已解析修饰器。回调上下文只提供 set_modifier(stat, "add"|"base_percent", value)、change_health(amount)、get_state(key) 和 set_state(key, value)。属性最终值统一为初始值加固定加值总和，再加初始值乘比例总和。Client 可读取同步的 snapshot()，但不执行生命周期回调。

systems.block_placement 管理逐格方块放置工作、运行态恢复、物品预留和失败释放。UI 通过通用 2D selection 选择空位并提交 core:block_placement.confirm；engine.block_placement.settle 是受限 Host 结算入口，只接受当前正在派发的匹配 Build 完成事件、相同 payload 方块和单个对应物品预留，并再次校验 placeable、空位、支撑与碰撞。系统也会持久化带 growth_target/growth_ticks 的已放置方块，到期后通过权威世界方块写入链路完成变换。

systems.building_design 是建筑设计工作区与建造工作之间的桥。工作区草稿以绝对世界坐标记录，因此提交时不需要额外的锚点步骤；core:building_design.build（工作区"开始建筑"按钮）把草稿单元交给 systems.block_placement，由后者统一负责工作发布、物品预留和结算。只有支撑已经存在于世界中的单元会被提交，其余保留在队列里并按 20 tick 的节拍重试，因此多层设计自下而上逐层成型，而不是在提交时就把上层单元全部判为缺少支撑。每轮最多校验并提交 512 个单元（放置校验会按殖民者逐个复查单元），窗口在整轮无进展时轮转，避免一段无法建造的单元永久遮蔽后面的单元。已经排入工作池、或世界方块已经等于设计方块的单元视为已完成，会同时离开队列和草稿；被其它方块占用、超出世界范围、或缺少可放置定义的单元保留在草稿中并作为原因上报，不会静默丢弃。提交被接受后工作区会自动关闭（等同按下退出设计），把玩家交回运行中的世界；被拒绝的提交（草稿为空或无效）保持工作区打开以便修正，已经接管的单元离开草稿，因此下次进入工作区只会看到仍在等待建造的部分。

engine.building_design.draft() 返回 active/valid/errors/cells（单元含 block_id/block_hash/x/y/z/direction，自下而上排序），engine.building_design.remove_cells(cells) 删除对应单元并刷新工作区。

远端客户端走同一条命令：工作区草稿是本地引擎状态，因此客户端在 payload.cells 中附带自己的草稿单元，Host 用同一套提交流程建造；systems.building_design.submit(remote_cells) 在 remote_cells 非 nil 时按该列表提交且不修改 Host 本地草稿，返回结果的 cells 字段列出 Host 已接管的单元，客户端据此清理自己的虚影。Host 回包由 C++ 在独立锁下交接、并在主线程应用，因为设计工作区归主线程所有；客户端正是靠这份回包关闭自己的工作区。

蓝图文件库不在 Lua 侧：core:building_design.new/name/new_folder/folder/folder_up/save/save_as/rename/delete_entry/open_file 由引擎在主线程直接处理，工作区面板自己就是文件浏览器（文件夹行进入子目录、蓝图行打开并等待落点、每行自带删除按钮），**不调用系统文件对话框**；这些命令不经过命令桥的 building_design.* 转发，也不返回"未实现"占位原因。core:building_design.build 仍然走原有转发路径。蓝图文件存放在可执行文件旁的 blueprints/，保存时坐标以最小角为原点相对化，打开后需要点击地面选择落点，蓝图才会写入草稿。

定时器

定时器按模拟 tick 执行，不是按真实时间。

engine.timers.after(20, function(tick)
  engine.log.info("runs once at tick " .. tostring(tick))
end)

local timer_id
timer_id = engine.timers.every(100, function(tick)
  engine.log.info("heartbeat " .. tostring(tick))
  if tick > 1000 then
    engine.timers.cancel(timer_id)
  end
end)

天气

天气由版本化动态天气区域状态提供。MOD 可以读取当前天气和指定区块的局部天气、最终温度、战斗环境及表现接口，用于作物、事件、音效或 UI 展示；未在文档中定义的区域移动/切换公式不会由 API 猜测。

local weather = engine.weather.get()
if weather.precipitating then
  engine.log.info("weather: " .. weather.type .. " intensity=" .. tostring(weather.intensity))
end
local local_weather = engine.weather.at_chunk(chunk_x, chunk_z)

专项规则需要直接切换已存在区域时，可调用 engine.weather.set_region(region_id, weather_id, intensity_level)；天气定义、强度档位和区域必须已经由 MOD 数据注册，API 不生成默认天气规则。

确定性随机

math.random 在脚本环境中会报错——这是有意为之，确保跨平台和跨存档确定性。需要脚本随机数时使用 engine.random，它会在引擎初始化、新世界和读档时用世界 seed 重置。

local roll = engine.random.int(1, 100)
local chance = engine.random.float()

if engine.random.bool() then
  engine.log.info("rolled " .. tostring(roll) .. " chance=" .. tostring(chance))
end

engine.random.seed(42)
local debug_roll = engine.random.int(1, 6)

end)

地形扩展

地形 API 提供世界初始化后的只读查询。群系和地物只能通过 data/biomes 与 data/features 注册；世界生成由 C++ TerrainGenerator 加载 JSON 数据，不存在 Lua worldgen 注册旁路。旧普通矿脉注册入口已移除，矿物由 mine_rules 的区块矿井契约提供。

function M.on_world_init()
  local h = engine.terrain.height_at(0, 0)
  engine.log.info("height at origin: " .. tostring(h))
end

NPC 阵营

data/factions、data/faction_spawn_rules 和 data/diplomacy_proposals 只保留注册 schema。NCDOCS 尚未定义其他殖民地的生成、关系变化、提案结算或谈判推进规则，因此 CoreMod 的这些内容目录为空，新世界不会随机生成 NPC 阵营。

local defs = engine.factions.list_defs()
local instances = engine.factions.list_instances()
local relations = engine.factions.pair_relations()
local proposals = engine.factions.proposal_defs() -- CoreMod 当前为空

for _, faction in ipairs(instances) do
  local status = engine.factions.diplomatic_status(faction.id)
  engine.log.info(faction.display_name .. ": " .. status)
end

Lua 当前只公开定义、实例、双边关系、提案 schema、谈判记录和外交状态的读取接口，以及名称模板工具。没有 spawn、spawn_initial、关系修改、提案执行或谈判写入 API；玩家可见界面固定显示“接口未定”。其他殖民地实例只能由未来有文档依据的专项规则显式加入。

网络命令

网络 API 用于联机和命令同步。内容型 MOD 不建议把核心玩法依赖放在网络回调里。详情见网络同步。

engine.network.send_ui(target, payload) 是经营数据桥的低级 Host 提交入口，返回 pending 状态；engine.network.is_handling_command() 只用于数据桥识别 Host 正在执行已接收命令并防止递归提交。普通 MOD 应调用 engine.ui.command.run，由 CoreMod 自动区分本地表示操作与 Host 权威玩法操作。

if engine.network.is_connected() then
  engine.log.info("network mode: " .. engine.network.mode())
end

本地化

如果需要翻译 UI 文本，可以用 engine.locale 相关 API。翻译文件放在 lang/，locale ID 使用 en-us、zh-cn 这样的文件名形式。详情见 本地化与翻译。

engine.locale.set_locale("zh-cn")
local locale = engine.locale.current_locale()
local text = engine.locale.translate("ui.menu.start")
engine.log.info(locale .. ": " .. engine.locale.translate_cat("ui", "menu.start"))
需要查函数签名时看 Lua API 速查。那一页有搜索框，适合用 focus、inventory、terrain 之类关键词快速过滤。
