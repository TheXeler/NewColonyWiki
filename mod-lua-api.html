入口脚本结构

mod.json 里的 entry 指向入口脚本。脚本运行后返回一个表，引擎读取表里的生命周期函数。不需要实现全部四个——只写你需要的即可。

local M = {}

function M.on_load()
  engine.log.info("[copper_age] data loaded")
end

function M.on_world_init()
  engine.log.info("[copper_age] world is ready")
end

function M.on_tick(tick, dt)
end

function M.on_shutdown()
  engine.log.info("[copper_age] shutdown")
end

return M

四个生命周期函数的用途：

  • on_load —— 适合订阅事件、注册要闻条件、读取配置和恢复非世界领域状态。此时数据与完整领域 API 已绑定，但世界还没生成。
  • on_world_init —— 适合生成世界相关内容、初始实体、注册 terrain biome/ore/feature。此时地形 API 已可用。
  • on_tick(tick, dt) —— 每帧执行。这个地方的逻辑要尽量轻，不要在每帧做大规模扫描。
  • on_shutdown —— 清理工作，比如写日志。

读取和操作实体

实体属性通过 engine.entities.attribute(uuid, key) 统一读取。Server 使用 engine.entities.add_attribute(uuid, key, type, value, source) 新增 Map 值，set_attribute(uuid, key, value, source) 修改已有基础值，remove_attribute(uuid, path) 删除 Map 键或点号前缀下的值。增已有键、改不存在键会记录 ERROR 并拒绝该次操作；这些修改接口不返回成功标志。C++ 包装层区分 ECS 引擎字段与 Map 属性。实体生成使用 spawn(id) 或 spawn(id, payload)，完整构建参数可由 default_payload(id) 复制后修改。物品、生产、掉落、治疗和招募仍经过各自的 Server 权威事务。引擎物理开关可通过 engine.ecs.get_gravity_enabled(entity) 和 engine.ecs.get_collision_enabled(entity) 查询，由 Server 使用对应设置接口修改；set_collision_enabled 同时影响地形碰撞。

只控制实体之间的接触时，Server 可调用 engine.ecs.ignore_entity_contacts(uuid)、ignore_collision_pair(first_uuid, second_uuid) 或 ignore_collision_prototype(uuid, prototype_id)。每次成功注册返回非零句柄，失败返回 0；规则持续有效，调用 engine.ecs.remove_collision_rule(handle) 移除。engine.ecs.add_collision_filter(function(first_uuid, second_uuid, first_prototype, second_prototype) ... end) 注册全局过滤器，同样返回句柄。过滤器在实体接触判断时运行，返回 true 允许、false 跳过；任一规则跳过即不产生该对实体的接触，其他规则仍可独立移除。过滤器应只读取数据，不在接触回调中修改世界。回调失败或返回非布尔值时记录一次错误，并按允许碰撞处理。涉及已销毁实体的规则自动移除；换世界及成功重载 Mod 时清除规则，Mod 应在世界载入或后续 tick 重新登记。规则不保存到存档，也不影响地形碰撞。

engine.combat.soldiers() 返回按队长和槽位排序的兵模行，每行包含 entity_uuid、leader_uuid、从零开始的 slot 与当前位置 x/y/z。该接口只提供状态；阵型换位和碰撞豁免关系由 Mod 决定。

local current_hp = engine.entities.attribute(entity_id, "current_hp")
local max_hp = engine.entities.attribute(entity_id, "max_hp")
engine.log.info("health: " .. tostring(current_hp) .. "/" .. tostring(max_hp))

Server Lua 的 engine.combat.commit_damage(target_uuid, damage) 是正整数伤害的权威提交入口。兵模目标归到队长的共享血池，血池大于零时先扣血池，退场兵模数量由原生层按剩余比例计算；没有血池时扣目标／队长生命。返回 {ok, shield_damage, health_damage, shield_remaining, health_remaining, visible_soldiers}；失败时只有 ok=false。CoreMod 自动近战通过 systems.combat_damage.submit 调用该入口。

CoreMod 的 systems.combat_damage.submit({source_uuid, target_uuid, damage}) 接受 Lua 命中逻辑给出的最终伤害，校验后调用原生权威入口；成功后发送不可取消的 core:combat_damage_committed 通知。同一目标正在结算时，嵌套提交返回 damage_reentrant。近战命中与伤害由 systems.combat_melee 处理，远程弹体命中调用武器 Lua 的 on_hit，由回调选择提交伤害或弹开。

systems.combat_melee.resolve(attacker_uuid, defender_uuid, hit_roll, penetration_roll) 从 battler.* 读取解析属性；兵模通过 engine.combat.attribute_owner(uuid) 使用队长属性。按需求文档计算命中率与穿透率：两者均将“攻击值−防御值+35”钳制在 10%～90%；返回两阶段结果与未取整的 melee_power。两次随机抽样由调用方提供，范围为 [0,1)。穿透失败与非整数伤害的最终提交规则仍待裁定，此函数不会提交伤害。

engine.combat.melee_contacts() 返回当前世界的 {attacker_uuid, target_uuid} 数组：征召小队队长、血池仍在的征召兵模，以及带袭击身份的有效 battler 可主动近战。已征召兵模处于 Peace 时也可被接触和受伤。其他未征召 battler 的出手由声明 melee_attack 的 Reaction 许可；袭击者被其他 Reaction 接管时也遵循该限制。原生层选择近战范围内明确敌对的对象，袭击者优先征召目标，同级按距离和 UUID 稳定选择；玩家攻击指令仍优先。注册表有多份有效 combat_rules 且缺规则归属时返回空数组。engine.combat.claim_melee_attack(attacker_uuid, target_uuid) 在服务端重新核对目标并领取该实体的一次出手机会；成功时按内容冷却 tick 更新可再次出手时间。冷却组件随实体保存和同步。接触查询与领取本身都不提交伤害。2026-10-11 修改尚未编译或运行。

engine.combat.hostility(first_uuid, second_uuid) 返回 {resolved, hostile}。它把兵模归到队长；实体带有殖民地实例 UUID 时按该实例解析并校验派系哈希，没有 UUID 时只在派系定义哈希唯一匹配运行实例时解析。缺失或歧义时 resolved=false，不能把它解释成友好。

engine.combat.alert_target(leader_uuid) 返回警戒半径内最近、可明确判为敌对且有 battler.is_battler 能力的实体 UUID；没有目标或派系实例无法唯一解析时返回空字符串。CoreMod 的战斗 tick 使用该结果触发和平小队入场；脱战退出和多实例归属仍未完成。

实体能力属性

engine.entities.set_engine_component(uuid, "inventory_slots", {slots=N}) 修改 ECS 基础背包槽数，物理容量由基础值和当前修正计算；N 必须是 0 到 4294967295 的有限整数，无效输入保持原状。缩容时将受影响预约的释放、裁掉槽位全部物品的落地和容量变更一起提交，成功后中断关联 Task。落地点从实体经统一属性接口解析后的当前位置向上并向外搜索空气方块；不以固定搜索半径拒绝缩容。

set_engine_component(uuid, "job", values) 和 set_engine_component(uuid, "career_progress", values) 用于生成后初始化职业组件。提供的 level、xp、rank 必须是有限的非负整数，并分别处于无符号 32 位、有符号 32 位、无符号 32 位范围内；任何字段无效时整次写入失败，原组件保持不变。

实体原型通过 capabilities 声明属性值或引用属性包。属性包在生成实体的最后一步展开为 <name>.<value_name> 形式的 Map 键；省略 name 时从默认 pack ID 的短名推导。实体 JSON 不接受 attachments 字段。

"capabilities": [
    { "type": "pack", "name": "battler", "default": "core:battler_attributes",
      "custom_values": [{ "type": "float", "name": "attack", "default": 2.0 }] },
    { "type": "int", "name": "custom_value", "default": 0 }
]

name 和 custom_values 均可省略；覆盖项也可以声明 pack 中没有的新属性。生成和运行时添加 pack 都把其根键保存为 pack 类型并立即展开子键；展开时找不到模板会报告 ERROR 并拒绝。engine.entities.attribute(uuid, "battler") 返回 {type="pack", value="core:battler"}；attribute(uuid, "battler.*") 返回以相对子键为索引、解析值为内容的 table，如 melee_hit 或 magic.spell.cooldown。position.* 等 ECS 节点同样返回 table。Lua 通过 engine.entities.has_node(uuid, path) 检查完整键或点号前缀、engine.entities.add_attribute(uuid, key, type, value, source) 增加单值或 pack、engine.entities.add_attribute(uuid, capabilities, source) 展开并增加整组声明且记录来源、engine.entities.set_attribute(uuid, key, value, source) 修改已有基础值。修改 pack 根键只更改备查模板 ID，不改变已展开的运行时子键；改为未注册 ID 允许写入并报告 WARN。删除 pack 根键会一并删除其展开子键。move_speed、vision_range、current_hp、max_hp、needs.*、mood.* 和 condition.* 等引擎字段使用同一读取与修改接口，具体存储由 C++ 分流。

engine.entities.add_attribute(uuid, capabilities, source) 的运行时批量参数只接受属性值声明和 pack 引用；job 等 ECS 组件声明会使整次添加被拒绝并记录 ERROR。engine.entities.default_payload(id) 返回可修改的完整生成参数，并为未写 name 的 pack 引用填入从原默认 pack ID 推导的能力槽名。Lua 随后可改该引用的 default，再调用 engine.entities.spawn(id, payload)；能力槽名保持不变，生成后按这个前缀展开为 Map 键。

物品与方块附件

物品与方块定义仍可声明 attachments 数组；每项写明 id、type 和 default。这套附件声明不用于实体能力。

物品附加数据是所有者槽或地面堆的 components 内容。腐坏和地面消失事件按地面堆实体 UUID 或库存所有者及槽位报告变化，不提供独立的物品实例附加数据句柄。

物品句柄失效后，每个操作都会像键不存在一样失败，写操作返回 false。

engine.events.subscribe("item:ground_despawned", function(event)
    local item = event.item
    if not item or not item:valid() then return end
    if item:has("yourmod:freshness") then
        item:set("yourmod:freshness", 0.0)
    end
end)

物品附加数据随存档往返、随网络同步，并参与同类物品的堆叠合并判定（附加数据不同的两堆不会合并）。物品定义可以写 attachments 数组声明键与默认值。

方块也有附件表。凡是负载里带数值 x／y／z 的事件都会给出 event.block，包括方块事件与相应的工作事件。

engine.events.subscribe("block:interacted", function(event)
    local block = event.block
    if not block or not block:valid() then return end
    block:attach("yourmod:tended_at", event.tick or 0)
end)

区块未加载时方块句柄操作返回失败；读取不会为了附件创建区块。方块附件目前只存在内存里，卸载区块即丢失。

合成和职业

Server Lua 用 engine.jobs.register_transition_checker(fn) 注册转职资格规则。应在世界加载完成或 Mod 重载提交后的服务端事件回调中注册；候选 Mod 加载期间不能在模块顶层调用此接口。回调参数依次为实体 UUID、目标职业 ID 和候选物品 ID；只检查职业前置时第三项为空字符串，校验具体装备及提交预约时传物品 ID。允许时返回 true，拒绝时返回 false, reason，其中 reason 是非空原因码。可通过 engine.jobs.definition(id)、engine.jobs.transition_state(uuid) 和 engine.items.definition(item_id) 查询职业、进度与装备声明。资格查询和转职提交前使用同一回调；未注册或回调返回无效结果时拒绝转职。engine.jobs.commit_transition 返回 success, reason；提交时资格回调拒绝的原因原样作为第二个返回值，供 core:career_blocked 事件显示。

engine.jobs.definition(id).level_abilities 为每级天赋提供修正声明、pack 名列表 pack_names，以及已展开的 capabilities 列表（每项含 name、type、value）。engine.jobs.transition_state(uuid).history 按保存顺序列出职业 ID 哈希与等级；CoreMod 的 systems.career.active_abilities(uuid) 使用当前职业、父职业、前置职业及历史保留标记选择生效天赋。engine.attributes.groups(uuid) 读取实体当前运行时修正组的来源、组 ID 和数值项。仅 LogicServer 可调用 engine.entities.attribute_sources(uuid)，它返回运行时新增属性键到来源 ID 的映射；来源元数据不随客户端实体快照同步。由缺失修正目标隐式生成的零值键标记为 engine:modifier_target，职业 Lua 可以在安装同名能力前清理它。engine.entities.base_attribute_keys(uuid) 只列出 Map 中实际存储的基础键，不触发修正目标的隐式创建。Lua 据此同步职业能力属性与修正组，C++ 负责解析定义和保存职业进度。

engine.attributes.replace_groups(removed, replacements) 按实体 UUID、来源和正整数 group_id 批量移除或替换修正组。替换项另含 values 数组，每项为 {stat, mode, value}，其中 mode 是 add 或 base_percent。候选世界先应用全部移除与替换，再校验每个受影响实体的最终属性；中间组合不会单独拒绝。涉及 inventory_slots 时，在候选世界中准备所有受影响背包的扩缩容和落地物品，预约释放与修正组一起发布；任何一个实体准备失败都拒绝整批，原世界、预约和修正组保持原状。提交后才中断受影响的 Task。一次性数值操作使用 engine.attributes.apply_once(uuid, stat, mode, amount, source)，模式同样为 add 或 base_percent；它直接改变基础值，不创建修正组，百分比按操作前基础值计算。

配方和职业本体写在 JSON 里。公开直通制作和职业分配入口均已禁用；Lua 可以查询配方，并通过 CoreMod 生产订单和装备换装事务创建实际工作。

engine.attributes.set_group、remove_group 和 replace_groups 的 group_id 必须是 1 到 9007199254740991 之间的整数，即 LuaJIT 数字可以精确表示的范围。replace_groups 的更新项及每组 values 都必须是连续数组；输入无效时拒绝整批。

engine.entities.attribute(uuid, "inventory_slots") 通过统一属性接口读取 ECS 基础槽数与修正计算后的容量；解析值必须落在 0 至 4294967295 的整数范围内，越界修正会被拒绝。生成定义省略顶层槽数时默认为 0。Server 属性写入、一次性操作，以及 Lua 或引擎内部提交、移除修正组后都会同步物理背包槽数；临时修正移除后按保留的基础槽数恢复容量，缩容使用相同的预约与落物事务。

职业天赋的 capabilities 只接受属性值声明和 pack 引用；job 等 ECS 组件声明会在职业定义加载时被拒绝。运行时新增属性的来源与值分开保存。职业 Lua 根据生效天赋删除不再生效的能力键，再用通用属性接口新增获得的键；仍生效的能力键保留当前值。删除前会检查点号路径下的后代是否也属于本次删除，避免误删其他来源的值；父子键都要删除时先删子键。职业变更已经提交后才同步玩法效果，失败仅报告错误，不回滚职业进度。其他来源的 Mod 属性保持原样。engine.entities.remove_attribute(uuid, path) 删除精确键和点号路径下的全部后代键，并清除各键的来源记录。

CoreMod synchronizes active career ability and equipped item modifiers through engine.attributes.replace_groups after profession assignment, crafting experience, native Task experience, recruitment, world loading and Mod reload. A Task completion only submits changes when its awarded experience leaves the desired groups different from the current groups. Career groups use a core:career_ability: source followed by the ability ID; the single equipment slot uses core:equipment. C++ aggregates these submitted groups and does not apply career or equipment bonus declarations directly.

for _, recipe_id in ipairs(engine.crafting.list_recipes()) do
  local recipe = engine.crafting.get_recipe(recipe_id)
  if recipe then
    engine.log.info("recipe: " .. recipe.id .. " -> " .. recipe.output.id)
  end
end

CoreMod 菜单通过 systems.production.queue 建立可重复或维持库存的订单，再由 systems.crafting.queue 预留所有者槽材料并在 core:task_completed 后结算。完成回调使用 engine.tasks.settle_craft_outputs(reservation_ids, products, state_commit) 在候选世界中一起扣取材料、生成全部地面实体产物并清理 pending 记录；任一来源、产物或状态提交无效会拒绝整次结算。Lua 不提供直接制作入口。

engine.designs.attribute_ids() 返回只读且有序的引擎属性名表（26 项，索引 1..26），顺序与 Engine/Simulation/AttributeStats.hpp 一致。物品基型的 base_values 键、attributes[].id 以及品质表的 modifiers[].attribute 都取这份名单，表外名字在配置期被拒绝。编辑器与工具应以该入口生成属性下拉，不要再各自硬编码副本。

engine.designs 提供锻造基型和不可变设计方案接口。list_item_bases()/get_item_base(id, civilization_index?) 返回基型、科技解锁状态、属性/词条等级、容量、材料与配置错误；preview(base, attributes, affixes) 只计算方案；save(...) 仅允许已解锁基型并始终创建新 design ID，即使方案因容量或选择错误而无效。list()/get(id) 返回已保存方案。方案没有名称或批量数量字段。

工作池

发布工作时必须指定工作所属阵营。faction_id 使用数据 ID 哈希，玩家/殖民地工作通常使用 core:player。AI 只会领取与自己阵营一致的工作。

TaskPool 内部使用 TaskTag、TaskCategory、TaskTargetKind、TaskAction 和 TaskPayloadKind。Lua 可发布已注册的任务类型；目前没有公开的任务类型注册 API，也不保留旧工作接口兼容入口。

engine.tasks.post(type, faction_id, x, y, z, duration, payload_id, target_entity) 的类型包含 move、build、repair、mine_operation、haul、craft、use_medicine、transfer_patient、job_change、treat、feed_patient、first_aid、battlefield_treat、guard 和 patrol，并接受源码中列出的同义类型。move 使用目标坐标，允许零时长；Mod 应指定执行实体，任务由该实体沿 TaskPool 导航路径完成。其他类型仍按各自规则校验时长。未知类型或无效参数返回 nil。target_entity 是可选实体目标；非零 payload_id 作为 Custom payload 保存。一次性 Mine/Chop 只能由指定工具确认后经 Server 命令创建；研究工作只由已付款的研究项目派生。

Server Lua 用 engine.tasks.register_speed_callback(fn) 注册 Task 速度计算。回调在 Task 开始执行时接收实体 UUID、Task UUID 和数字 Tag，返回有限正数倍率；同一次执行只调用一次。未注册时倍率为 1。回调报错或返回无效值会中断并延后该 Task，不推进本次进度。CoreMod 在 Lua 中读取统一属性接口计算各类工作速度；缺失的可选倍率属性按中性值 1 处理，存在但不是数字或非有限数的属性会报错。

Command results include target and an error code on failure. If execution raises an exception, the result also includes detail for the player-facing error message. The core:zone_created event is emitted after a zone is created with zone_uuid, type_id, and instance_id. Core stockpile zones register an outdoor_stockpile policy and Lua hauling chooses a vacant cell in the zone, carries the item there, and leaves it as a non-recoverable ground pile without a despawn timer. At activation, hauling limits the claimed count to the worker's available backpack stack capacity; a larger ground pile is moved in multiple trips. Zone removal removes the policy. The final optional boolean of engine.tasks.return_carried_claim_to_ground requests a permanent ground pile.

local player_faction = engine.util.data_id_hash("core:player")
local task_id = engine.tasks.post("haul", player_faction, 16.5, 65.0, 16.5, 3.0, 0)

底层执行不再查找数据驱动 action 注册表。引擎根据目标类型、Interact/Destroy、工作标签和 payload 语义处理方块交互、规划方块放置、实体攻击或脚本事件。

订单元数据可用 engine.tasks.set_metadata(task_id, source_id, priority, designated_worker?) 写入；普通优先级范围为 1-9，0 保留为特殊优先级。engine.tasks.set_qualification 可要求指定职业和等级。需要物品的工作使用 engine.tasks.set_item_requirements(task_id, rows) 声明领取时材料资格；每行使用 count 与 item_id/candidates 定义候选集合。领取按已加载方块所有者槽位的可用数量检查，不提前占有；在 core:task_activated 后使用 reserve 或 reserve_owner_item 预留。普通库存记录没有独立实例号，工作材料资格拒绝旧 instance_id 字段。set_available/available/reserved/reserve/commit_reservation/release_reservation 暴露资源预留接口。

公共工作先进入殖民者个人队列，领取本身不触发预留。领取初选和未激活队列继续执行共用职业、工作计划、状态、路径与当前材料可满足性条件。调度器每轮按稳定殖民者顺序让每名空闲且合格的殖民者至多认领一项；后一名殖民者只会从前者尚未认领的工作中选择，因此优先形成 A、B、C 的均匀分配，不再先填满某一人的队列。个人队列上限仍为 20 项。AI 每 5 tick（250 ms）检查一次公共池，已有个人工作时不会补领或被更高优先级工作抢占。

队列中的一项真正激活后才触发 core:task_activated，制作等经营系统在此时申请资源和位置预留。激活检查失败时可调用 engine.tasks.activation_failed(task_id)，它会把该项退回公共池、清理导航并阻塞 20 tick；执行者随后尝试队列下一项。engine.tasks.set_locked(task_id, true) 复用同一个 blocked_until_tick 字段写入永久阻塞哨兵，任务继续存在但不能被领取；传入 false 会把阻塞时间恢复到当前 tick 并立即解锁。完成结算与下一项激活分属不同 tick，避免下一项在上一项提交前抢先预留。

取消和中断分别触发 core:task_cancelled 与 core:task_interrupted。engine.tasks.interrupt_all(worker) 会把当前激活项和整条个人队列全部退回，释放激活项未提交预留；其他殖民者可立即领取，原殖民者在 20 tick 内跳过这些工作。

engine.tasks.suspend(task_uuid) 暂停 Build/Craft/Mine/Cut/Repair，保留任务 UUID、进度、项目步数与业务记录，并通过中断通知释放未消耗预约及工作点。返回 false 表示任务不支持、已无效或旧生命周期通知仍在处理，需要由调用方判定并重试。engine.tasks.resume(task_uuid) 等待清理通知确认后解暂停，不解除独立锁定／冷却。Task 快照提供 suspended、preserve_progress；暂停过的经济任务在后续资源领取失败时仍保留进度。暂停任务仍 is_valid，但不能领取、推进或完成。生产订单 pause/resume 保留原 Task 成员并持久化操作意图；搬运和战斗等任务需要专项资产交接，不使用此通用接口。

搬运是唯一允许同批多项同时激活的类型。CoreMod 只合并来源坐标、物品堆叠键、来源位置和目标仓储位置都兼容的项，并按背包格、单格堆叠与搬运容量截断。engine.tasks.claimed(worker) 提供该人尚未激活的队列，engine.tasks.personal_load(worker) 与 engine.tasks.personal_limit() 给出个人队列的加权负载与上限（摧毁/放置体素类工作每项占 1 格、其他类型每项占 10 格，总上限 20；人员界面的“当前工作数量”即显示该负载），engine.tasks.activate_claimed_haul(task_id, worker) 只允许激活其中的 Haul 项；各项仍独立保存来源、数量、目标格和预留，并由 AI 逐项导航结算。合成系统在成功创建每个产物实例后立即调用搬运系统的幂等入库入口发布 Haul 工作，周期扫描仅作为遗漏恢复。没有有效仓储目的地时自动搬运任务仍会发布，但使用永久冷却哨兵锁定；目的地出现后自动解锁。拆分物品堆时，原始来源实例会保持占用到当前批次交付完成，防止携带者被同一堆的新取货任务抢走；交付结算后立即扫描剩余来源并发布下一批，不等待周期扫描。

寻路失败会被记为 error；AI 不再因导航目标不可达而生成原地 fallback 工作。

如果 AI 在执行中被中断（例如殖民者倒地、死亡、低需求触发个人需求，或 AI 状态被外部清空），当前激活项和未激活个人队列都会返回工作池；只有激活项可能持有预留。恍惚只影响命中率，不会单独中断工作。

engine.economy_log.record(spec) 向统一经营日志追加结构化正常/异常记录；engine.economy_log.entries(filter?) 只读查询并支持 worker、source_id、source_object_id、item_id、task_tag 和 problem_id 筛选。engine.problems.report(spec) 按来源与问题 ID 上报或刷新持续问题，list(filter?)/alerts() 返回局部问题和同类聚合警报，resolve(instance_id) 解除并自动写日志。个人进食工作按殖民者保持唯一；暂时找不到或无法预留食物时只冷却并重试同一工作，不记录逐次激活失败，也不上报普通缺粮问题。殖民者进入会持续损失生命的严重饥饿阶段后，才产生按人数聚合的全局持续警报。问题 API 只表达文档已有的阻塞/失效反馈，不应创建新的玩法规则。

systems.work_policy 保存工作计划和排班模板、殖民者分配及个体覆盖。六个工作计划开关依次为搬运、建造、维修、制作、采集、职业；排班的 24 个小时槽取值为 0=睡眠、1=工作、2=自由。工作时段可领取普通工作，自由时段只领取特级工作并允许社交/娱乐，睡眠时段不领取普通工作；进食、休息、逃跑、紧急急救和即时威胁响应不受这些开关限制。模板修改会重新计算全部使用者的有效策略。没有工作策略组件或尚未配置六类开关时，普通工作固定拒绝；网络实体载荷也不提供全开启缺省值。

engine.colonists.work_policy(entity) 返回有效开关、小时表、模板 ID 和覆盖掩码；engine.colonists.set_work_policy(entity, spec) 是模板系统写入有效状态的低级接口。玩家界面通过 work_policy_state 快照及 core:work_plan.*、core:schedule.*、core:work_policy.* 命令管理模板，不直接修改 AI 内部类别优先级。

订阅事件时保存返回的 handler id，之后可以取消订阅。优先用事件响应具体变化，不要在 on_tick 里反复扫描所有实体。

local handler = engine.events.subscribe("inventory:changed", function(evt)
  if evt.item_key == "copper_age:copper_ingot" then
    engine.log.info("copper ingot changed by " .. tostring(evt.delta))

end, 10)

装备系统

装备组件只有一个固定槽位：Equipment。Lua API 使用 equipment.item 表示当前装备，不支持旧的主手、副手、护甲、饰品槽，也没有双手占槽规则。

-- 从方块容器的指定槽换入唯一装备槽
engine.ui.command.run("core:colonists.change_equipment", { entity_uuid = entity_id, source_x = x, source_y = y, source_z = z, source_slot = slot })

-- 已进入职业后不能单独卸装；这里只读取当前装备
local current = engine.equipment.get_slot(entity_id, "Equipment")
engine.log.info("current item: " .. tostring(current.item_id))

-- 查询实体所有栏位
local eq = engine.equipment.get_equipment(entity_id)
engine.log.info("equipment: " .. tostring(eq.Equipment.item_id))

-- 查询单个栏位
local held = engine.equipment.get_slot(entity_id, "Equipment")
if held.item_id ~= "" and held.count > 0 then
  engine.log.info("equipped item: " .. tostring(held.item_id))
end

上述装备查询的 item_id/id 为定义字符串，空槽为 ""，不返回内部数字编号或库存 UUID。返回独立内容快照，包含 components 及品质、词缀、效果、载荷、腐坏进度和附件字段；修改返回表不改变实体装备。居民装备详情和 engine.inventory.inspect 使用同样的内容来源。engine.colonists.detail(entity).equipment.item.attributes 是按顺序排列的装备修正项，每项包含 stat、mode 和 value；展示修正时应读取它们，stats 映射只保留各属性的数值。

统一物品与玩家仓储

普通库存内容归所有者：实体背包使用 ECS Inventory，方块容器使用按坐标存储的 OwnerInventory，地面单品堆使用 ECS GroundItemPile。槽内容为 {id,num,components}，其中 id 是定义字符串 ID；槽记录没有独立 UUID。地面堆具有普通实体 UUID；部分拾取保留实体，整堆拾取删除实体。只有定义和完整组件一致，且定义与槽容量都允许时才能合堆；地面堆还要保持相同的产出工作点、消失倒计时和回收许可。

engine.items.owner_inventory(entity_uuid)、block_inventory(x,y,z)、ground_pile(entity_uuid) 与 ground_piles() 返回所有者内容快照。owner_sources() 提供可预约来源；engine.tasks.reserve_owner_item 创建按所有者和槽位定位的预约。预约释放在候选实体世界和方块内容中共同发布；失败保留原句柄供重试。预约句柄是数字，任务引用使用任务 UUID 字符串，地面堆身份使用实体 UUID。engine.items.total/available/reserved 和 storage_snapshot() 汇总玩家方块仓储。

engine.items.colony_sources(colony_uuid, item_id_or_ids) 按殖民地实例 UUID 和单个物品 ID／哈希或连续数组检索可用来源。结果包含 source、item_id、item_hash、未预约数量 count 和坐标；仅计入归属该殖民地的方块库存及其户外储存区内允许的地面堆。放置工作的领取预检和激活预约均按此范围检索。用户名与殖民地 UUID 的绑定只用于服务端 C++ 原生命令校验；Mod 自有传输不经过该自动校验。

服务端物品操作包括 pickup_ground_pile、drop_inventory_slot、deposit_ground_pile_to_block、deposit_inventory_slot_to_block 和 withdraw_block_slot_to_inventory。地面堆预约通过 engine.tasks.reserve_owner_item 建立，公开的孤立句柄预留／释放入口已移除。直接物品接口拒绝工作预约系统正在管理的句柄；搬运在激活时预约来源与目的槽容量，领取后通过 engine.tasks.* 事务把预约转到搬运者背包槽，到达后按同一句柄存入。制作完成使用 engine.tasks.settle_craft_outputs 一次提交材料和全部产物；采矿完成调用 items.create(spec, state_commit)，受管状态提交成功后才发布地面堆。产物规格只接受当前字段，词缀和效果必须是连续字符串数组，旧物品实例字段会被拒绝。items.create 返回每堆的 entity_uuid 和数量；无真实工作完成上下文会拒绝。腐坏与地面消失在引擎 tick 推进，通知携带地面堆实体 UUID 或库存所有者及槽位。

生存、饮食和治疗

engine.tasks.current_tag_for_entity(uuid) 返回该实体在本模拟 tick 实际推进过的 Task 数字标签；未推进 Task 时返回 nil，完成的最后一个 tick 仍可查询。CoreMod 对连续执行 Rest（2）或 Sleep（3）的每 10 tick 结算一次精力恢复，恢复量是配置中的 fatigue_recovery_per_second 乘以 0.5；第 10 tick 结算。未执行这两种 Task 时进度清零。进度保存在 condition.fatigue_recovery_ticks。AI 负责选择和推进 Task，不直接修改疲劳值。

engine.colonists.detail(entity) 返回 condition、injuries、死亡/倒地状态、阶段进度、心情崩溃计时与印象。engine.colonists.survival_configuration() 返回唯一 colonist_survival_rules 记录的引擎基础配置状态与错误 ID；状态效果 ID、字段和数值由 CoreMod Lua 校验。Server 的 core:tick 监听器使用 engine.entities.is_simulation_active(uuid) 按统一属性接口解析后的实体位置判断强加载区，跳过区外实体，再逐实体读取 needs.*、mood.*、condition.*、生命值、位置与温度，调用 Lua 生存计算函数，并通过统一属性接口提交需求消耗和状态。状态倍率由 Lua 映射到目标属性，以 core:survival_status 来源的通用修正组提交；没有变化时不重复提交。战斗属性修正只在 battler.is_battler 为真时加入。重复的 condition.*_multiplier 快照字段已删除，使用 engine.attributes.groups(uuid) 按来源查询生存修正，使用统一属性接口查询最终值。药物冷却槽的计时仍由 C++ 处理。心情系统继续处理印象及状态带来的心情贡献。进食和治疗通过各自的 Server 权威事务提交；食物与治疗模板由 CoreMod Lua 管理。

心情系统经统一属性接口读取解析后的 condition.mood_offset 作为状态心情贡献，同时用基础 mood.mood_value 和此前已应用的偏移计算持续心情底值。加入或移除该属性的修正组时，下一次心情更新会重新计算贡献；印象的衰减仍由心情系统负责。

systems.survival.advance_health 只接收活动状态效果汇总后的伤害速率；严重饥饿伤害来自 status_effects.malnutrition.damage_per_second，不另设独立速率。CoreMod 将该值设为每秒 1 滴，在 20 TPS 下每 20 tick 扣 1 滴；不足 1 滴的进度保存在实体状态中。advance_dying 计算倒地、稳定、死亡和濒死进度；advance_breakdown 计算压力阶段、恍惚和崩溃计时。仅 LogicServer 可调用 engine.difficulty.get() 读取需求速度、环境状态、恢复窗口倍率和死亡开关。生存配置数值必须能表示为 ECS float；超出范围的 JSON 数字会拒绝整份配置。

engine.colonists.set_medicine_slot_capacity 是系统应用个人通用药剂 CD 槽上限的低级入口；reserve_medicine_slot、commit_medicine_slot 和 release_medicine_slot 分别对应药剂使用工作激活、成功和失败/中断。medicine_slots 返回总数、预留数、占用数、药剂物品 ID 和剩余秒数。CoreMod 从唯一 medicine_slot_rules 数据记录读取基础容量和科技增量；systems.medicine.slot_capacity_state(entity) 返回期望/实际容量、预留、占用、逐槽状态、容量来源和配置错误。CoreMod 当前基础容量为 2，状态显示在人员界面的个人信息中；记录缺失时仍保留 medicine_slot_rules_missing 屏障。

engine.json.decode(text) 在基础 Lua API 绑定阶段注册，因此 MOD 的 on_load 可以把 engine.modding.get_data_json(type, id) 返回的原始 JSON 解码为 Lua 值；空字符串或无效 JSON 返回 nil。engine.runtime_state.set(key, table) 和 get(key) 提供按稳定 key 保存 JSON 兼容 Lua 值的低级状态仓。状态仓可由异步存档线程安全快照；系统应在状态变化后写入，并在 on_world_init 中恢复。玩法领域载荷必须保存当前 schema_version = 1 并拒绝明确的未知版本；项目尚未发布，不维护旧领域结构的兼容读取。函数、userdata 和循环表不能作为持久化值。

engine.colonists.memorials() 返回死亡殖民者的实体 ID、姓名、职业、等级、死亡 tick 和位置；纪念记录会写入 world.json。建筑治疗点 API 详见建筑蓝图注册。

engine.buildings.raid_target() 返回当前袭击目标的 valid、稳定错误 ID、建筑实例/定义、角色、价值、位置和当前难度 raid_multiplier。选择顺序固定为已完成城镇大厅优先，否则最高价值玩家建筑；该接口不创建袭击，也不定义额外的袭击公式。

engine.buildings.repair_status(instance_id) 和 repair_statuses() 返回耐久、配置上限、授权、材料、职业、工作量、单元恢复量和稳定问题 ID。damage 是战斗/事故提交建筑伤害的低级接口；set_repair_authorized 是 Server 授权入口，apply_repair_unit(task_uuid) 只在匹配 UUID 的 Repair 工作完成派发期间结算，目标建筑从原生任务 payload 取得，不由脚本重复指定。CoreMod systems.repair 负责 Repair 工作、激活预留、原子提交、取消释放和经营日志；玩家操作走 building.repair_authorize Server 命令及 building/repairs 数据通道。

engine.buildings.storage_points() 和 storage_point_status(id) 返回稳定位置 ID、建筑/定义、坐标、容量、冷藏、存在/可用及永久失效原因。CoreMod systems.building_storage 将可用点安装成通用 storage_voxel 策略并进入 building/storage_points 通道；损毁/拆除时通过 engine.items.drop_block_inventory_contents 将方块所有者内容拆成地面堆实体，并清理关联预留。

engine.buildings.instances() 返回权威建筑实例的稳定 ID、定义 ID、状态和原点。CoreMod systems.world_components 保存部件 UUID、类型、定义、owner、逐格坐标/hash 和产出表引用。树干 core:tree 的 tree_feature: "core:oak" 指向多方块树形；首次割除从 engine.terrain.generated_tree_at 的明确生成集合登记树组件，树苗生长从 tree_cells 的完整形状登记。系统不会从相邻同类方块推断归属。engine.world.grow_tree(feature_id,x,y,z,sapling_hash) 是 Server 生长批量提交入口，校验原树苗、其余空位和实体占用，再整体写入树干与树叶；失败保留树苗，供后续重试。已有组件使用保存的完整集合。缺少树组件或方块已改变时分别报告 tree_component_missing、component_target_invalid。

伐木和野生植被采集合并为 Cut（工作编号 15，显示“割除”），选择工具 ID 为 core:cut，命令为 core:orders.confirm_cut，完成通知为 core:block_cut。2D 区域按整列查找目标，树归并到根部并去重。树按完整组件结算，野生食物仍按单格产出表结算；测试食物的原有产出和随机 Tick 刷新规则保留。

engine.terrain.ecology_chunks() 返回当前强加载区块的坐标、主群落、基础/最终温度（摄氏度）和树木统计；engine.terrain.ecology_animals() 返回实际存活动物实体、原型、攻击性和位置。CoreMod systems.ecology 按两类生态内容表推进刷新，并通过 core:ecology 运行态保存资源点索引和逐规则/区块的下次检查 tick；snapshot()、resource_point_at(x,y,z) 和统一 ecology/state 数据通道提供只读接口。空内容表不扫描世界并报告稳定配置问题。

CoreMod systems.trade_points 把玩家放置的 core:trade_point 方块当作商队泊位：一个贸易点容纳一个来访商队。系统提供 list()、available()、counts()、point_at(x,y,z)、reserve(x,y,z,owner)、release(x,y,z,owner)、release_owner(owner) 和 arrival_status()；占用是运行时状态，世界加载或卸载时清空。未放置贸易点时返回 trade_point_missing，全部被占用时返回 trade_points_all_occupied；系统不在缺少贸易专项规则时生成商队、价格或交易结算。贸易点是放置部件而不是世界地点，因此没有 world/locations 通道，也没有 location.trade_point.* 命令。

engine.visibility.configuration() 返回唯一视野规则的配置状态；state_at(cx,cz) 返回 unexplored/explored/visible，chunks() 返回全部探索记忆与当前可见标记。未探索区块不提交地形渲染；已探索但不可见区块只保留地形记忆，不提交活动实体；当前可见区块显示地形和实体。待登记新人不作为视野源。探索记忆写入 world.json 并沿 save_state:world Server 通道复制。

职业等级按节点独立保存在 CareerProgress；切换职业会保存原节点等级并恢复目标节点既有等级。存档恢复要求履历包含 jobs 数组；Job 和履历中的 ID、等级、阶位必须是 32 位无符号整数，重复或超出容量的已知职业履历会拒绝加载，不会静默覆盖或截断。未知职业 ID 会记录 ERROR，并保留当前 Job、履历、已展开的属性 Map、属性来源和修正组；缺失的 Mod 恢复后再由 Lua 同步职业效果。engine.colonists.career_tree(entity).levels 返回全部已有职业等级，equipment_options 返回目标职业当前可选择的具体玩家仓储装备实例。engine.colonists.list() 和普通摘要不构建职业树；只在显式请求 career_tree(entity) 时检查各职业与装备选项。engine.jobs.set_career_level 只接受带有效 PendingRegistration、当前 Job 等级为 0 且其定义 max_level:0 的候选人，用于一次性写入候选履历，不能修改正式殖民者职业。提供的等级须是目标节点范围内的有限整数；无等级节点只接受 0，越界值会拒绝而不夹到范围内。经验入口只处理注册表中存在且 max_level 大于 0 的职业；未知职业或零级职业不会获得经验。

engine.colonists.list() 与 detail(uuid) 的居民摘要通过统一属性接口读取 needs.*、mood.* 和 condition.*；摘要仍返回原有的心情比例、需求、状态和伤病名称字段。实体缺少对应组件时，需求和心情沿用零值默认展示。

CoreMod 食物计划使用 engine.entities.attribute(uuid, "needs.hunger") 的解析值选择合适营养量。旧的 engine.ecs.get_needs/get_mood 直接组件读取入口已删除；Mod 应通过统一属性接口读取对应字段。

待登记新人带有 PendingRegistration 状态。engine.colonists.find_recruitment_entry 遍历当前已加载区块，使用 VisibilitySystem 的真实三态视野选择距当前可见区最远且实际可寻路到大厅的位置；它不把强/半加载半径解释为玩家视野。待登记实体不扩展可见区、不领取工作、不推进生存伤害并按中立目标处理。抵达大厅后由招募系统解除该状态。

systems.potion 只从注册表读取 medicinal_herbs 与 potion_trait_effects，并由效果记录的公共区间边界构建四项独立效果表。系统另提供剂型固定材料、科技/容量许可、设计预览和保存。六种剂型倍率及 0-4 级基础 CD 由设计文档固定；药材和效果内容为空时不会生成默认条目，也不能保存无效果配置的药剂设计。configuration() 及 snapshot().configuration 返回 valid/errors/herb_count/interval_count/registered_trait_effect_count/missing_effect_ids，snapshot().trait_effects 暴露加载结果和来源路径。空表分别报告 potion_herbs_missing 和 potion_trait_intervals_missing；缺少 Lua 生命周期定义时按具体效果 ID 报告 potion_effect_definition_missing。configure_form_material(form, item_id, count, recipe_id) 将剂型关联到固定配方；秘粉的 item_id=nil/count=0，其他剂型固定材料数量必须为 1。关联配方必须使用成败模式。

已保存药剂设计通过生产订单进入兼容工作点，激活时统一预留逐味药材和剂型固定材料、送入输入暂存，完成时使用配方的标准成败/产出表并原子提交。目标剂型物品的成品载荷严格只写效果表和最终 CD，不写药材序列、计算过程或设计名称；重复效果 ID 原样保留。失败会消耗材料但不生成受制造模式影响的目标。

systems.medicine.queue(user, target, owner_source, duration, faction_id) 发布隐藏的药品使用行为。激活时通过 engine.tasks.reserve_owner_item 预留指定所有者槽位内容，并预留目标的空药品 CD 槽；完成后消费一份内容、应用载荷效果并用载荷 final_cd 占槽。失败、中断或取消释放所有者内容预约和槽，其他进食行为不受没有空槽影响。治疗模板同样按具体药剂所有者内容读取最终 CD，不再允许模板另填 CD。NCDOCS 尚未定义用药动作本身的工作时长，因此 duration 缺失或非正数时固定返回 medicine_task_duration_undefined，不会回退到私有的 1 秒默认值；治疗、急救、病号喂食和患者转移使用同样的显式屏障。

systems.effects 通过 register_definition(effect_id, definition) 注册 instant、modifier_start、modifier_tick 和 modifier_end。每次成功用药建立独立效果组；组记录药品实例、目标、CD 槽、组内剩余时间、JSON 状态和已解析修饰器。回调上下文提供 set_modifier(stat, "add"|"base_percent", value)、apply_once(stat, "add"|"base_percent", value)、get_state(key) 和 set_state(key, value)。属性最终值为基础值加固定加值总和，再加基础值乘比例总和；各项修正独立计算，整数属性在全部贡献相加后才取整。基础值改变时重新计算缓存中的比例贡献，移除修正后缓存回到剩余修正对应的值。Client 可读取同步的 snapshot()，但不执行生命周期回调。

systems.block_placement 管理逐格方块放置工作、运行态恢复、物品预留和失败释放。UI 通过通用 2D selection 选择空位并提交 core:block_placement.confirm；engine.block_placement.settle 是受限 Server 结算入口，只接受当前正在派发的匹配 Build 完成事件、相同 payload 方块和单个对应物品预留，并再次校验 placeable、空位、支撑与碰撞。系统也会持久化带 growth_target/growth_ticks 的已放置方块，到期后通过权威世界方块写入链路完成变换。

systems.farming 为小麦种植区派翻地和播种 Build 工作、成熟收获 Cut 工作，并保存生长阶段。CoreMod 不定义种子物品：播种与补种完全不消耗物品，不设置材料要求，农业待办也不持有任何物品预约；农业没有需要清理的历史播种材料或旧预约，恢复只校验坐标、阶段与任务身份。world.settle_farming(task_uuid,zone_id,crop_id,phase) 为 Server 的匹配 Build 完成结算入口，校验区域、任务、耕地、空位和碰撞后原子放置幼苗；world.advance_crop(zone_id,crop_id,x,y,z,stage) 校验区域、耕地和预期阶段后推进一阶段。world.is_chunk_loaded(x,z) 提供 Server 已加载区块查询，农业只推进已加载区块。get_block_info 的 crop_id 标记让收获保留种植区，产物形成可回收地面堆。详见作物数据。

systems.building_design 是建筑设计工作区与建造工作之间的桥。工作区草稿以绝对世界坐标记录，因此提交时不需要额外的锚点步骤；core:building_design.build（工作区"开始建筑"按钮）把草稿单元交给 systems.block_placement，由后者统一负责工作发布、物品预留和结算。只有支撑已经存在于世界中的单元会被提交，其余保留在队列里并按 20 tick 的节拍重试，因此多层设计自下而上逐层成型，而不是在提交时就把上层单元全部判为缺少支撑。每轮最多校验并提交 512 个单元（放置校验会按殖民者逐个复查单元），窗口在整轮无进展时轮转，避免一段无法建造的单元永久遮蔽后面的单元。已经排入工作池、或世界方块已经等于设计方块的单元视为已完成，会同时离开队列和草稿；被其它方块占用、超出世界范围、或缺少可放置定义的单元保留在草稿中并作为原因上报，不会静默丢弃。提交被接受后工作区会自动关闭（等同按下退出设计），把玩家交回运行中的世界；被拒绝的提交（草稿为空或无效）保持工作区打开以便修正，已经接管的单元离开草稿，因此下次进入工作区只会看到仍在等待建造的部分。

engine.building_design.draft() 返回 active/valid/errors/cells（单元含 block_id/block_hash/x/y/z/direction，自下而上排序），engine.building_design.remove_cells(cells) 删除对应单元并刷新工作区。

远端客户端走同一条命令：工作区草稿是本地引擎状态，因此客户端在 payload.cells 中附带自己的草稿单元，Server 用同一套提交流程建造；systems.building_design.submit(remote_cells) 在 remote_cells 非 nil 时按该列表提交且不修改 Server 本地草稿，返回结果的 cells 字段列出 Server 已接管的单元，客户端据此清理自己的虚影。Server 回包由 C++ 在独立锁下交接、并在主线程应用，因为设计工作区归主线程所有；客户端正是靠这份回包关闭自己的工作区。

蓝图文件库不在 Lua 侧：core:building_design.new/name/new_folder/folder/folder_up/save/save_as/rename/delete_entry/open_file 由引擎在主线程直接处理，工作区面板自己就是文件浏览器（文件夹行进入子目录、蓝图行打开并等待落点、每行自带删除按钮），**不调用系统文件对话框**；这些命令不经过命令桥的 building_design.* 转发，也不返回"未实现"占位原因。core:building_design.build 仍然走原有转发路径。蓝图文件存放在可执行文件旁的 blueprints/，保存时坐标以最小角为原点相对化，打开后需要点击地面选择落点，蓝图才会写入草稿。

天气

天气由版本化动态天气区域状态提供。MOD 可以读取当前天气和指定区块的局部天气、最终温度、战斗环境及表现接口，用于作物、事件、音效或 UI 展示；未在文档中定义的区域移动/切换公式不会由 API 猜测。

local weather = engine.weather.get()
if weather.precipitating then
  engine.log.info("weather: " .. weather.type .. " intensity=" .. tostring(weather.intensity))
end
local local_weather = engine.weather.at_chunk(chunk_x, chunk_z)

engine.weather.temperature_at_world(x, z) 返回该世界坐标所属区块的最终温度（摄氏度，引擎气候范围为 -20 至 40）；坐标必须是有限且位于 32 位世界坐标范围内。生存 Lua 计算可用实体解析后的 position.x 与 position.z 查询局部温度；作物、生态规则和殖民者舒适温度使用同一口径。

专项规则需要直接切换已存在区域时，可调用 engine.weather.set_region(region_id, weather_id, intensity_level)；天气定义、强度档位和区域必须已经由 MOD 数据注册，API 不生成默认天气规则。

2026-10-13 实际历史查询 engine.weather.interval_at_chunk(cx,cz,from_tick,until_tick) 返回 available／reason；成功有 from_tick、until_tick、basis_tick、revision、天气／区域身份、类型、强度、final_temperature、原开始／计划切换 Tick与光照／视野／表现等效果。请求需为安全整数且终点不超过当前引擎 Tick；成功区间从请求起点开始，在下一次真实变化或请求终点截止，调用方可沿 until_tick连续读取。过去的计划切换时点不改写实际已经发生的天气；未来预测仍不能越过未知天气。历史来自实际切换／覆盖／定义重载，缺历史或未来时点明确拒绝，查询不写状态。set_region 现在沿共享玩法写入权限拒绝客户端／权威准备内修改；可选第四参数 Tick只能等于当前引擎 Tick，不能补写过去。原生／抽象农业共用 Farming.weather_interval(plot,from,at) 并验证历史版本与起点；缺完整历史时原生保留地块进度时点供重试，抽象拒绝该候选。旧文件只有载入起点后的历史，不用当前温度代替过去温度。天气移动／切换公式仍由策略提供；本批仅静态检查，未编译／运行验收。

engine.network.send_ui(target, payload) 是经营数据桥的低级 Server 提交入口，返回 pending 状态；engine.network.is_handling_command() 只用于数据桥识别 Server 正在执行已接收命令并防止递归提交。普通 MOD 应调用 engine.ui.command.run，由 CoreMod 自动区分本地表示操作与 Server 权威玩法操作。

if engine.network.is_connected() then
  engine.log.info("network mode: " .. engine.network.mode())
end
