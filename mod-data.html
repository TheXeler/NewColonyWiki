注册物品、方块和规则

所有内容数据都放在 data/ 下。引擎在加载阶段自动扫描这些目录，不需要你在 Lua 里手动注册。

通用规则

不管哪种数据类型，下面几条规则是通用的：

  • 每个 JSON 都必须有唯一的 id，推荐格式 <mod_id>:<name>。
  • 引用其他内容时必须写完整 ID，比如 copper_age:copper_ingot。
  • 配方、职业、文明和方块掉落会做跨引用校验。引用不存在会导致 MOD 加载失败，引擎会报出具体是哪个文件和哪条记录。
  • 文件可以放在对应类型目录下的任意位置（包括子目录），只要文件在正确的类型根目录下即可。例如 data/blocks/materials/copper.json 和 data/blocks/copper.json 都行。
  • 当前引擎支持 21 种数据类型：blocks、tags、entities、recipes、jobs、civilizations、techs、focuses、factions、faction_spawn_rules、diplomacy_proposals、name_pools、features、ores、crops、buildings、terrain、biomes、combat、audio、zones。

方块（blocks）

方块是体素世界的基本构成单位，放在 data/blocks/ 下。stack_size 表示一个背包格子能堆叠多少个，范围 1~999。category 用来分类，可以取 material、tool、food、equipment 等。

{
  "id": "copper_age:copper_ingot",
  "name": "Copper Ingot",
  "stack_size": 64,
  "category": "material"
}

方块既是世界中的体素单元，也是库存中的物品——没有单独的"物品"类型。hardness 决定挖掘所需时间，drops 里的 ID 必须指向已注册的方块。

{
  "id": "copper_age:copper_ore_block",
  "name": "Copper Ore",
  "hardness": 3.0,
  "drops": ["copper_age:copper_ore"]
}

工作台类的方块（如 workbench、stone_furnace）还会声明关联的配方类型或可用操作。

材质

方块材质用于决定每个面的显示贴图。当前 data/blocks/*.json 只负责注册方块数据，不能单独通过新增 texture 字段让方块换贴图；实际渲染贴图由渲染器的方块材质注册表加载。

内置内容目前有两类材质来源：

  • NewColonyTextures/*.json + .png：Blockbench / Minecraft Bedrock 风格的模型 JSON 和贴图图集。JSON 里的 elements[0].faces 声明六个面的 UV，PNG 会按 16x16 tile 切入纹理图集。
  • 程序生成 fallback：没有材质映射的基础方块会按固定颜色生成临时纹理，例如 stone、wood、leaves、water 等。
{
  "texture_size": [64, 64],
  "elements": [
    {
      "from": [0, 0, 0],
      "to": [16, 16, 16],
      "faces": {
        "north": { "uv": [0, 0, 4, 4], "texture": "#0" },
        "east":  { "uv": [0, 4, 4, 8], "texture": "#0" },
        "south": { "uv": [4, 0, 8, 4], "texture": "#0" },
        "west":  { "uv": [4, 4, 8, 8], "texture": "#0" },
        "up":    { "uv": [4, 12, 0, 8], "texture": "#0" },
        "down":  { "uv": [12, 0, 8, 4], "texture": "#0" }
      }
    }
  ]
}
这部分仍属于渲染器内部能力，不是稳定的 MOD 数据接口。内容型 MOD 现在可以安全依赖 data/blocks/ 的注册、掉落和堆叠行为；自定义方块材质需要等材质映射被暴露为正式的 MOD 配置后再作为稳定接口使用。

实体原型（entities）

实体原型用于 spawn_proto 控制台命令和 engine.ecs.spawn_prototype。放在 data/entities/ 下。一个实体由多个组件拼成，每个组件描述一种能力或属性。

当前实体原型 JSON 解析器只读取下表中的组件；有些 ECS 组件虽然可在运行时存在，但不会从原型 JSON 直接读取。

组件描述
Position世界坐标 (x, y, z)
Speed移动速度向量
Health生命值 (current, max)
Needs两项需求 (hunger, fatigue)
Mood心情值 (mood_value, 0~100)
HeldItem手持物品 (item_id, count)
Equipment单一装备栏，数据字段为 item，包含当前装备的物品 ID 和数量。
Job职业 ID 和等级 (1-6)
Name显示名称
ColonistTag殖民者标记（用于查询过滤）
AIStateAI 状态（行为树 ID, 当前节点, LoD 层级, busy 标志）
Stats力量、敏捷、智力、耐力和工艺等属性。
Visual实体渲染模型和贴图。
Animationbiped 程序动画参数。
HeadVisual头部纹理和朝向数据。

Rotation 和 Scale 是 Lua/运行时组件，可用 engine.ecs.set_rotation 和 engine.ecs.set_scale 添加；AIState 原型生成实体时会自动附加 WorkerPriorityConfig、NavAgent、BlockInteractor 和默认职业；PrototypeRef 由原型生成流程自动记录。

下面是一个殖民者的实体原型示例：

{
  "id": "copper_age:copper_worker",
  "components": {
    "Position": { "x": 0, "y": 64, "z": 0 },
    "Speed": { "x": 0, "y": 0, "z": 0 },
    "Health": { "current": 100, "max": 100 },
    "Needs": { "hunger": 40, "fatigue": 20 },
    "ColonistTag": {},
    "AIState": { "behavior_tree_id": 0, "current_node": 0, "lod_level": 0 },
    "Job": { "id": "copper_age:coppersmith", "level": 1 },
    "Name": { "data": "Copper Worker" },
    "HeldItem": { "id": "core:stone_chunk", "count": 1 }
  }
}

工作标签与动作

工作系统使用 WorkTag、WorkTargetKind、WorkAction 和 WorkPayloadKind 描述一个归一化工作实例：前往目标位置，然后对实体、方块或规划方块执行 Interact 或 Destroy。

概念来源用途
WorkTagC++ 枚举细粒度工作标签，包含 Build、Mine、Chop、Haul、Craft、Research、Rest、Sleep 等。
WorkCategoryC++ 分类用于工人优先级、筛选和调度评分。AI 只会领取同阵营工作；faction_id 为 0 的工作会被拒绝。
WorkTargetKindC++ 枚举目标类型：Entity、Block 或 PlannedBlock。
WorkActionC++ 枚举硬编码底层动作：Interact 或 Destroy；不再有数据驱动 action 注册表。
WorkPayloadKindC++ 枚举payload_id 的语义类型：None、Block、Item、Recipe、Building、Zone 或 Custom。

当前公开的 Lua 发布入口仍是兼容形式 engine.work.post(type, faction_id, x, y, z, duration, payload_id)。type 支持 build/construction/plant、mine/dig/gather、chop、haul、craft/manufacture/cook、research、guard 和 patrol；未知字符串会落回 Build。这个入口默认发布 Block 目标工作，其中 mine/chop 使用 Destroy，其它标签使用 Interact；非零 payload_id 作为 Custom payload 保存。脚本驱动 work 主要通过 work:completed 处理完成逻辑；只有显式 Block payload 的 Block+Interact 会触发底层 block interaction。目前没有公开的 Lua 工作类型注册 API。

工作完成时引擎会发出 work:completed 事件，payload 包含 instance_id、worker、tag、category、target_kind、action、payload_kind、payload_id、faction_id、坐标、target_entity 和 tick。

配方（recipes）

配方放在 data/recipes/ 下。声明输入、输出和可选的职业要求。写了 Job 后，只有满足职业与等级要求的实体能制作。

{
  "id": "copper_age:smelt_copper",
  "inputs": [
    { "id": "copper_age:copper_ore", "count": 2 }
  ],
  "Job": { "id": "copper_age:coppersmith", "level": 1 },
  "output": { "id": "copper_age:copper_ingot", "count": 1 }
}

合成成功时会触发 recipe:crafted 事件，你可以在 Lua 里订阅它来响应。底层 engine.crafting.craft 仍是直接检查实体单个 HeldItem 的低级接口，多种输入或不同槽位输入不会在这条路径里自动汇总。

CoreMod 的制作菜单通过 systems.crafting.queue 下单：优先从 stockpile 账本预留输入材料，工作完成后把产物放入工人手中或存回账本。使用 stockpile 预留时 Craft 工作的 data 会置为 0，因此 C++ 工作完成路径不会再调用 RecipeSystem::craft 重复消耗或产出；只有未预留、依赖工人手持材料的低级制作才继续走 C++ 直接制作路径。

建筑蓝图（buildings）

建筑定义放在 data/buildings/ 下。建造菜单列出这些建筑蓝图；施工完成后，blueprint 中声明的方块会按建筑原点偏移放入世界。蓝图支持单点 pos，也支持闭区间长方体 from/to。

{
  "id": "copper_age:wood_hut",
  "name": "Wood Hut",
  "size": [5, 5, 5],
  "materials": [
    { "item_id": "core:wood_plank", "count": 72 }
  ],
  "construction_ticks": 240,
  "blueprint": [
    { "from": [0, 0, 0], "to": [4, 0, 4], "block": "core:wood_floor" },
    { "from": [0, 1, 0], "to": [4, 3, 0], "block": "core:wood" },
    { "pos": [2, 1, 0], "block": "core:wooden_door" }
  ]
}

materials[].item_id 和 blueprint[].block 都必须引用已注册方块/物品；所有蓝图坐标都必须在 size 范围内。完整说明见 建筑蓝图注册。

CoreMod 施工入口 systems.construction.order(def_id, x, y, z) 会创建建筑订单；材料足够时立即从 stockpile 账本预留并推进施工，材料不足时返回 { ok=true, status="waiting_materials", materials=..., missing=... } 并等待后续库存补足。等待订单会在 stockpile:changed 后立即重试预留，并每 60 tick 做一次兜底检查。systems.construction.preview_materials(def_id) 可用于只预览材料可用性，不会作为硬阻止。

HTML 建造面板读取 build_defs 快照，行结构为 { id, label, label_key, category, size, cost, materials, missing, available, can_order, status }；已下单建筑读取 construction_active 快照，行结构为 { instance_id, def_id, status, position, materials, missing, reserved_materials }。页面发送 core:build.begin { id } 时进入 placement；只有带 x/y/z 时才实际下单。

职业（jobs）

职业定义放在 data/jobs/ 下，旧 MOD 的 data/professions/ 会兼容注册为 jobs。职业声明转职需要的方块、前置职业、允许接取的 allowed_work_tags 和到达特定等级后解锁的配方；旧字段 allowed_work_types / allowed_job_types 也会作为迁移别名读取。等级范围 1-6，工作标签可使用 gather、mine、dig、build、plant、haul、craft、manufacture、cook、guard、patrol 等需求文档用语。完成玩家显式工作后按 100 * 当前等级 的阈值累计职业经验并升级，心情会把经验效率调整到 50%-150%。bonuses 会进入人员 UI 聚合属性；当前实际模拟已接入工作时长、搬运容量和作物收获成功率：mining_speed 影响挖矿/采集 work，construction_speed 或 work_speed 影响建造 work，crafting_speed 或 work_speed 影响制作 work，hauling_speed 或 carry_move_speed 影响搬运 work 进度，carry_capacity 影响搬运拾取掉落物时的一次携带数量，work_success_rate 影响成熟作物收获时每种产出额外 +1 的概率。战斗属性目前仍只保证展示。

{
  "id": "copper_age:coppersmith",
  "name": "Coppersmith",
  "category": "work",
  "max_level": 6,
  "required_block": { "id": "copper_age:copper_hammer", "count": 1 },
  "prerequisites": [
    { "id": "core:worker", "level": 1 }
  ],
  "unlocks_recipes": [
    { "id": "copper_age:smelt_copper", "level": 1 }
  ],
  "bonuses": [
    { "stat": "crafting_speed", "value": 0.10, "mode": "add_mult" }
  ]
}

分配职业成功时会触发 job:assigned 事件。category:"combat" 表示战斗职业；成功分配后会建立 Squad 和 CombatState。2026-07-20 V2 战斗不再为法师建立 ManaReserve。

战斗规则数据（combat）

战斗相关的非玩家设置默认值仍可放在 data/combat/ 下，作为 combat 类型进入通用数据注册表。2026-07-20 V2 战斗只实现近战基础循环，CoreMod 不再提供武器克制和压制规则表。

启动脚本默认值

CoreMod 的 Lua 启动脚本会读取 data/combat/bootstrap_defaults.json 中的 core:bootstrap_defaults 记录，用于不属于玩家设置、但适合随 MOD 内容版本调整的启动默认值。当前字段包括阵营关系事件的日长 tick、触发时刻、概率、关系变化量、随机 salt，以及初始殖民者生成的 x/z 坐标。缺少该记录或缺少单个字段时，bootstrap.lua 会回退到脚本内默认值，保持旧版启动行为。

运行时交战规则、命中公式、攻击冷却和测试命令说明见 战斗规则。

文明（civilizations）

文明用来把职业、开局选项和配方限制组织在一起。放在 data/civilizations/ 下。目前建议保持简单：声明可用职业、一个开局选项，需要时再加配方限制。

{
  "id": "copper_age:copper_clan",
  "name": "Copper Clan",
  "jobs": ["copper_age:coppersmith"],
  "starting_options": [
    {
      "id": "copper_age:starter",
      "blocks": [
        { "id": "copper_age:copper_ore", "count": 4 }
      ],
      "jobs": [
        { "id": "copper_age:coppersmith", "level": 1, "count": 1 }
      ]
    }
  ]
}

焦点事件

焦点是展示给玩家的消息。放在 data/focuses/ 下。条件可以是内置条件（tick_at_least、entity_count_at_least、entity_count_at_most、colonist_need），也可以是 Lua 注册的自定义条件。

{
  "id": "copper_age:copper_found",
  "title": "Copper Discovered",
  "body": "Your colony can start working copper.",
  "severity": "info",
  "one_shot": true,
  "conditions": [
    { "type": "tick_at_least", "tick": 20 }
  ],
  "choices": [
    { "id": "ok", "label": "OK" }
  ]
}

NPC 阵营（factions）

阵营定义放在 data/factions。name_template 可以包含 ${random_name}，生成实例时会从指定的名称池里取词；关系值会被限制在 min_relation 和 max_relation 之间。

{
  "id": "copper_age:merchant_guild",
  "name_template": "${random_name} Merchant Guild",
  "initial_relation": 10,
  "max_relation": 100,
  "min_relation": -100,
  "name_pools": ["copper_age:metals"]
}

阵营自动生成规则（faction_spawn_rules）

开新世界时引擎会按 data/faction_spawn_rules/ 下的规则文件批量 spawn AI 阵营实例，让世界开局就存在若干 NPC 势力。每个文件包含一个 id（信息字段）和一个 rules 数组；每条规则指定一个 faction_def_id 和 [min_count, max_count] 区间，引擎用世界种子派生的独立随机流在每个区间内取一个数，按数量 spawn 该阵营。引用未知 def 的规则会被跳过并警告。max_count=0 的规则不生效。Lua API：engine.factions.spawn_initial(seed?)、engine.factions.list_spawn_rules()；控制台命令：spawn_initial_factions [seed]。

{
  "id": "core:default",
  "rules": [
    { "faction_def_id": "core:barbarian_tribe", "min_count": 1, "max_count": 2 },
    { "faction_def_id": "core:pirate_band", "min_count": 0, "max_count": 1 },
    { "faction_def_id": "core:merchant_guild", "min_count": 1, "max_count": 2 },
    { "faction_def_id": "core:scholar_order", "min_count": 0, "max_count": 1 }
  ]
}

每个阵营实例加入世界时（自动 spawn、控制台 spawn_faction / spawn_initial_factions、Lua engine.factions.spawn / spawn_initial）都会发布 faction:spawned 事件，payload 字段：instance_id、def_id、faction_hash、display_name、relation、min_relation、max_relation、inclination、spawned_tick、reason。reason 取值：initial（开局自动 spawn）、console（控制台命令）、script（Lua API）、spawned（缺省）。Lua 订阅示例：engine.events.subscribe("faction:spawned", function(evt) ... end)。

外交提议（diplomacy_proposals）

外交提议放在 data/diplomacy_proposals/。每个文件定义一个 id、effect、required_status 和可选的 relation_offset、maximum_base_score、treaty_id、forced。提议可在谈判 API 中被反议、接受或拒绝。

名称池（name_pools）

名称池给 NPC 阵营生成名称使用。放在 data/name_pools/ 下。words 必须是字符串数组，空数组会被跳过。

{
  "id": "copper_age:metals",
  "words": ["Copper", "Bronze", "Tin", "Verdigris"]
}

地物（features）与作物（crops）

验证命令

在控制台中用这些命令确认数据注册成功：

list_data blocks prefix=copper_age:
list_data recipes prefix=copper_age:
list_data buildings prefix=copper_age:
list_data jobs prefix=copper_age:

实体视觉组件

实体原型可以声明 Visual 和 Animation。这两个组件用于客户端渲染，不改变职业、AI、背包等玩法数据。

组件字段说明
Visualmodel, texture, width, height, depthmodel 支持 box 和 biped。贴图路径相对 assets/。RimWorld/RimColony pawn 语义由 RimColonyCompact 的 Lua converter 转换成普通实体视觉数据；converter 可解析 RimWorld 风格 texPath 和 _south/_east/_west/_north 朝向贴图路径。
Animationenabled, walk_speed, walk_amplitude, idle_bob当前为 biped 程序动画，按实体水平速度驱动行走摆动。
 
"Visual": {
  "model": "biped",
  "texture": "textures/entities/copper_worker.png",
  "width": 0.45,
  "height": 1.80,
  "depth": 0.45
},
"Animation": {
  "enabled": true,
  "walk_speed": 6.0,
  "walk_amplitude": 35.0,
  "idle_bob": 0.015
}

如果实体贴图加载失败，引擎会使用 missing texture；这不会阻止实体模型和动画渲染。
