注册物品、方块和规则

所有内容数据都放在 data/ 下。引擎在加载阶段自动扫描这些目录，不需要你在 Lua 里手动注册。

通用规则

不管哪种数据类型，下面几条规则是通用的：

  • 每个 JSON 都必须有唯一的 id，推荐格式 <mod_id>:<name>。
  • 引用其他内容时必须写完整 ID，比如 copper_age:copper_ingot。
  • 配方、职业、文明和方块掉落会做跨引用校验。引用不存在会导致 MOD 加载失败，引擎会报出具体是哪个文件和哪条记录。
  • 文件可以放在对应类型目录下的任意位置（包括子目录），只要文件在正确的类型根目录下即可。例如 data/blocks/materials/copper.json 和 data/blocks/copper.json 都行。
  • 当前引擎注册类型包含 items、blocks、tags、entities、recipes、manufacturing_rules、quality_tables、output_tables、item_bases、experiences、medicinal_herbs、potion_trait_effects、hunting_rules、medicine_slot_rules、colonist_survival_rules、career_progression_rules、wild_food_rules、animal_distributions、weather_definitions、dynamic_weather_regions、visibility_rules、mine_rules、difficulty_rules、jobs、civilizations、techs、focuses、factions、faction_spawn_rules、diplomacy_proposals、name_pools、features、crops、buildings、terrain、biomes、combat、zones、audio；旧 professions 目录会存入 jobs 注册类型。

medicine_slot_rules 是可选的单记录全局表：base_capacity 必须为 1-16，technology_bonuses 为 {"technology_id":"mod:tech","slots":N} 数组，同一科技不可重复，基础值加全部科技增量不得超过 16。槽位是每个人都有的通用药剂属性，不限于治疗用途，并显示在人员界面的个人信息中。CoreMod 当前提供两个基础槽位；其他 MOD 若缺少此表，仍保留 medicine_slot_rules_missing 配置屏障。

colonist_survival_rules 是单记录生存规则表。需求与状态转换字段为 hunger_depletion_per_second、fatigue_depletion_per_second、need_work_duration_seconds、fatigue_recovery_per_second、depleted_stage_seconds、recovery_stage_seconds、temperature_stage_seconds、stress_mood_threshold、stress_recovery_mood_threshold、stress_stage_seconds、stress_recovery_stage_seconds、dazed_duration_seconds、well_fed_healing_per_second、dying_limit 和 dying_per_second。精力消耗使用统一字段，不自行增加昼夜差速或时间边界。需求工作时长与休息恢复速度必须来自该记录；缺失时不会回退到旧的 3 秒或每秒 6 点。压力在低心情或存在负面心情印象时恶化，只有心情达到恢复阈值且不存在负面印象时恢复；崩溃触发配置时长的恍惚，结束后压力降低一级。

career_progression_rules 是单记录职业成长规则表。work_experience 是成功完成一次可结算工作的基础经验，level_requirements 必须恰好包含四个正数，依次表示 1→2、2→3、3→4 和 4→5 级需求。NCDOCS 没有给出具体数值，因此 CoreMod 可暂时不提供记录；缺失时 engine.jobs.progression_configuration() 返回 career_progression_rules_missing，工作不会采用旧的 25/15 经验或每级 100 的公式。

status_effects 必须覆盖饥饿、极饿、营养不良、疲劳、过劳、昏睡、压力、崩溃、冻僵、冻伤、炎热、酷暑、恍惚、腿部骨折、手臂骨折和内伤的稳定英文 ID。每项通过 work_efficiency_multiplier、move_speed_multiplier、work_precision_multiplier、care_precision_multiplier、crafting_speed_multiplier、repair_speed_multiplier、melee_hit_multiplier、ranged_hit_multiplier、melee_block_multiplier、ranged_block_multiplier、attack_speed_multiplier、combat_move_speed_multiplier、vision_range_multiplier、ranged_range_multiplier、max_health_multiplier、mood_offset 和 damage_per_second 表达文档列出的效果；除可为负数的 mood_offset 外均不得为负。脑震荡不另设效果行，而是在运行时对腿伤和臂伤效果做去重并集；温度链冻伤与伤病冻伤也是同一效果。缺失、多记录或字段无效时保留稳定配置屏障，不回退到代码平衡值。CoreMod 可以暂不提供该内容记录。

wild_food_rules 每条记录声明具体资源点 block_id、食材 category、非空且不重复的 biomes、0-1 的 temperature_min/temperature_max、正整数 max_points_per_chunk、refresh_interval_ticks、spawn_attempts 和固定生命周期 post_harvest:"remove_and_refresh"。资源点方块必须引用现有产出表，才能通过一次性采集结算。animal_distributions 每条记录声明动物 entity_id、与原型一致的 aggression、群落/温度条件、base_cap_per_chunk、tree_cap_per_tree、max_cap_per_chunk、检查间隔、候选次数和 death_handling:"drop_and_refresh"；动物原型必须带 animal:true 和有效死亡产出表。两类内容表允许为空，但分别保留稳定全局配置屏障，不生成默认食材、动物、上限或刷新速度。

生态系统只检查强加载区块。区块加载与渲染范围以相机的绝对世界位置为中心，不使用环绕相机的观察目标代替相机位置。用户配置的渲染距离是地形绘制的硬外边界；线性 LOD 只在加载距离与渲染距离之间逐级降低细节，不额外扩大驻留或绘制范围。渲染距离内已驻留区块组成稳定聚合网格，相机高度、俯仰或旋转只更新视图参数并由 GPU 改写间接绘制可见性，不重新拼接或全量上传网格。卸载在渲染边界外保留两区块滞回，但滞回区块不会被绘制。强模拟集合进一步只包含已经提交到权威区块存储的驻留区块，并在卸载发生前发布；离开该集合的实体先冻结位移、碰撞和行走动画，新区块真正驻留后才解冻，因此缺失地形不会被物理系统解释为空气并触发坠落。区块提供主群落、基础温度、叠加当前天气修正后的最终温度和树木统计；动物上限按 min(max_cap_per_chunk, floor(base_cap_per_chunk + tree_count * tree_cap_per_tree)) 计算，因此伐木和植树会在后续检查改变上限。系统只补足低于上限的数量，不因上限下降删除现存动物；击杀后实体死亡产出照常结算，后续检查再补充。资源点是实际方块，动物是实际实体，均由既有区块/实体存档和网络路径保存；检查时重新核算当前对象。刷新候选由世界 seed、规则 ID、区块、检查代次和候选序号稳定决定。

visibility_rules 是可空的单记录视野规则表。它声明正整数 update_interval_ticks，非负 colonist_radius_multiplier 和 building_radius_multiplier，以及恰好 16 项的非负 light_multipliers（建筑索引对应合并光照 0-15）。天气的局部光照和视野影响来自 weather_definitions 对应区域状态，不在视野规则中重复声明。殖民者基础半径来自 ColonistAttributes.vision_range 并叠加状态及局部天气倍率；其当前视野是只使用绝对 XZ 坐标的 RTS 圆形范围，不读取 Y 坐标、所在高度光照或体素遮挡。建筑可用非负 vision_radius 提供玩家视野。镜头渲染距离内的地形始终提交；当前无视野时在体素光照、距离雾和颜色调整后保留色相并降低亮度。迷雾内实体保留权威数据但不生成模型。加载距离独立决定定位实体是否继续 AI、生存、心情、视野和物理模拟，处于只渲染外圈的实体保持冻结。记录缺失、多记录或无效时保留稳定全局屏障，不以加载或渲染半径作为玩法视野默认值。

视野距离、状态、地形明暗和实体模型剔除统一使用原始绝对 XZ 显示区块坐标；规范化星球坐标只负责区块数据和网格驻留。同一存储网格在不同环绕显示位置分别读取各自的绝对 XZ 视野状态。

新区块提交到权威区块存储后会对自身及光照传播半径内的已加载邻居安排一次最终光照网格重建。该过程不依赖生态资源点放置或其他后续方块修改，因此动物分布不会决定区块是否获得正常光照。

weather_definitions 按天气类型提供光照倍率、温度修正、视野倍率、战斗环境接口、表现接口和强度档位；类型严格为 clear、cloudy、rain、snow、fog。dynamic_weather_regions 提供稳定区域 ID、天气定义、覆盖区块集合、移动/切换策略和强度档位。运行时按区块查询区域天气、基础温度和最终温度；区域状态写入世界存档并随 Host 世界状态复制。文档未定义移动或切换公式时，配置屏障保留接口，不生成代码默认公式。

mine_rules 是单记录矿井规则表，声明矿井工作点类型、职业/等级、单次工作量、基础产量、每次基础耗减单位、矿物候选及权重、丰度档位权重/初始单位/产量倍率，以及按最低剩余比例选择的衰减产量倍率表。衰减表必须包含零阈值；引擎不内置最低产量倍率。difficulty_rules 也是单记录表，但不直接保存一套当前数值：dimensions 分别列出资源丰度、矿井衰减/耗尽、环境状态、需求速度、袭击、死亡和恢复窗口的稳定选项，presets 用选项 ID 组合预设，default_preset 指定数据定义的默认预设。预设和选项可用 label_key 提供本地化名称，并以 label 作为缺失翻译时的回退。倍率、矿井模式和死亡开关只来自所选选项；预设与选项引用会在加载时交叉校验。两表缺失或多记录时保留稳定配置屏障，不生成代码默认矿物、丰度、产量或难度。CoreMod 当前只有一组用于贯通系统的中性测试难度，不代表正式数值平衡。矿物物品引用必须存在。

旧 ores 体素矿脉目录不再加载。矿物不会作为普通矿物体素随机散布；世界种子和区块坐标稳定决定天然可见的矿物类型与丰度档位。带有 mine_rules.work_point_type 的建筑按工作点世界坐标实施每区块唯一约束，交互式放置预览会以 chunk_unique_work_point_conflict 拒绝第二座矿井。连续产物先进入该工作点输出暂存再由搬运清运。

地面物品即使由玩家殖民者行动、生产溢出或殖民者死亡产生，也保持 unowned 世界对象归属，只设置 recovery_authorized。搬运完成并进入露天仓储或储存体素时才原子改为玩家归属；当前存档直接保存这一结构。

每个地面物品实例同时进入只读渲染快照，并显示其中物品自身的缩小方块模型；没有完整模型时使用物品自身的方块贴图或图标生成代理，只有缺少这些资源时才回退到特殊方块 core:item_pile。该方块没有物品形态、不能由玩家放置，也不会写入或覆盖地形；物品种类、数量、归属和权威坐标仍只由 ItemSystem 管理。同一格的不同物品堆使用由实例 ID 决定的稳定偏移和朝向，不会逐帧抖动。

方块（blocks）

方块是体素世界的基本构成单位，放在 data/blocks/ 下。stack_size 表示一个背包格子能堆叠多少个，范围 1~999。category 用来分类，可以取 material、tool、food、equipment 等。

{
  "id": "copper_age:copper_ingot",
  "name": "Copper Ingot",
  "stack_size": 64,
  "category": "material"
}

方块是体素单元。新物品独立放在 data/items/，不需要成为可放置方块。可采方块的正数 hardness 直接表示一次性采掘/伐木工作时长秒数；缺失或无效时目标进入配置屏障。产物必须引用统一 output_table，旧 drops 不再属于当前 schema。

{
  "id": "copper_age:copper_ore_block",
  "name": "Copper Ore",
  "hardness": 3.0,
  "output_table": "copper_age:copper_ore_output"
}

工作台类的方块（如 workbench、stone_furnace）还会声明关联的配方类型或可用操作。

材质

方块材质用于决定每个面的显示贴图。当前 data/blocks/*.json 只负责注册方块数据，不能单独通过新增 texture 字段让方块换贴图；实际渲染贴图由渲染器的方块材质注册表加载。

内置内容目前有两类材质来源：

  • NewColonyTextures/*.json + .png：Blockbench / Minecraft Bedrock 风格的模型 JSON 和贴图图集。JSON 里的 elements[0].faces 声明六个面的 UV，PNG 会按 16x16 tile 切入纹理图集。
  • 程序生成 fallback：没有材质映射的基础方块会按固定颜色生成临时纹理，例如 stone、wood、leaves、water 等。
{
  "texture_size": [64, 64],
  "elements": [
    {
      "from": [0, 0, 0],
      "to": [16, 16, 16],
      "faces": {
        "north": { "uv": [0, 0, 4, 4], "texture": "#0" },
        "east":  { "uv": [0, 4, 4, 8], "texture": "#0" },
        "south": { "uv": [4, 0, 8, 4], "texture": "#0" },
        "west":  { "uv": [4, 4, 8, 8], "texture": "#0" },
        "up":    { "uv": [4, 12, 0, 8], "texture": "#0" },
        "down":  { "uv": [12, 0, 8, 4], "texture": "#0" }
      }
    }
  ]
}
这部分仍属于渲染器内部能力，不是稳定的 MOD 数据接口。内容型 MOD 现在可以安全依赖 data/blocks/ 的注册、掉落和堆叠行为；自定义方块材质需要等材质映射被暴露为正式的 MOD 配置后再作为稳定接口使用。

实体原型（entities）

实体原型放在 data/entities/ 下，一个实体由多个组件拼成。运行时只安装原型明确声明的组件，不会给普通动物补默认 Needs、AIState 或 Job。殖民者必须通过初始殖民地或招募登记链创建，动物必须由已注册的 animal_distributions 规则驱动；spawn_proto 只保留为开发者控制台诊断命令。

当前实体原型 JSON 解析器只读取下表中的组件；有些 ECS 组件虽然可在运行时存在，但不会从原型 JSON 直接读取。

组件描述
Position世界坐标 (x, y, z)
Speed移动速度向量
Health生命值 (current, max)
Needs两项需求 (hunger, fatigue)
Mood心情值 (mood_value, 0~100)
Equipment旧原型兼容输入。当前装备权威是统一物品系统中的单一装备位置实例，ECS 组件只作查询缓存。
Job职业 ID 和等级 (1-5)
Name显示名称
ColonistTag殖民者标记（用于查询过滤）
AIStateAI 状态（行为树 ID, 当前节点, LoD 层级, busy 标志）
ColonistAttributes文档定义的基础、工作和战斗属性；不包含力量、敏捷、智力或由它们计算的派生公式。
Visual实体渲染模型和贴图。
Animationbiped 程序动画参数。
HeadVisual头部纹理和朝向数据。

Rotation 和 Scale 是 Lua/运行时组件，可用 engine.ecs.set_rotation 和 engine.ecs.set_scale 添加；AIState 原型生成实体时会自动附加 WorkerPriorityConfig、NavAgent、BlockInteractor 和默认职业；PrototypeRef 由原型生成流程自动记录。寻路只计算并保存路线；实体 locomotion 层自行读取路线、推进路径点、决定速度与朝向，并维护 EntityAnimation 的播放状态和时钟。渲染器只采样该状态，并用当前 tick 内的视觉前瞻做平滑显示。

下面是一个可由原型接口直接创建的非殖民者实体示例：

{
  "id": "copper_age:pack_animal",
  "components": {
    "Position": { "x": 0, "y": 64, "z": 0 },
    "Speed": { "x": 0, "y": 0, "z": 0 },
    "Health": { "current": 100, "max": 100 },
    "AIState": { "behavior_tree_id": 0, "current_node": 0, "lod_level": 0 },
	"Name": { "data": "Pack Animal" }
  }
}

工作标签与动作

工作系统使用 WorkTag、WorkTargetKind、WorkAction 和 WorkPayloadKind 描述一个归一化工作实例：前往目标位置，然后对实体、方块或规划方块执行 Interact 或 Destroy。

概念来源用途
WorkTagC++ 枚举细粒度工作标签，包含 Build、Mine、Chop、Haul、Craft、Research、JobChange、Treat、Rest、Sleep 等。
WorkCategoryC++ 分类用于工人优先级、筛选和调度评分。AI 只会领取同阵营工作；faction_id 为 0 的工作会被拒绝。
WorkTargetKindC++ 枚举目标类型：Entity、Block 或 PlannedBlock。
WorkActionC++ 枚举硬编码底层动作：Interact 或 Destroy；不再有数据驱动 action 注册表。
WorkPayloadKindC++ 枚举payload_id 的语义类型：None、Block、Item、Recipe、Building、Zone 或 Custom。

当前公开的 Lua 发布入口是 engine.work.post(type, faction_id, x, y, z, duration, payload_id, target_entity?)。支持 build/construction/plant、repair、mine_operation、haul、craft/manufacture/cook、use_medicine/medicine/use_potion、transfer_patient/carry_patient、job_change/change_class、treat/treatment/heal、feed_patient/patient_feed、first_aid/stabilize、battlefield_treat/medical_pack、guard 和 patrol。未知类型、缺失或非正数时长固定返回 0，不创建其它类型工作。非零 payload_id 作为 Custom payload 保存，target_entity 可指定实体目标。一次性 Mine/Chop 只能由指定工具确认后经 Host 命令创建，研究工作只由已开启且已支付材料的研究项目派生；这些来源工作不能通过通用发布入口伪造。生产制作应通过生产订单，不应调用直通制作接口。目前没有公开的 Lua 工作类型注册 API。

工作完成时引擎会发出 work:completed 事件，payload 包含 instance_id、worker、tag、category、target_kind、action、payload_kind、payload_id、faction_id、坐标、target_entity 和 tick。工作取消或中断时分别发出 work:cancelled 或 work:interrupted，并包含 instance_id、worker、payload_id、faction_id、source_id 和 tick。

配方（recipes）

固定配方放在 data/recipes/ 下。声明输入、目标物品、产出表、兼容工作点和可选职业要求。实际结果及数量只由产出表决定；目标物品用于展示和维持库存统计。写了 Job 后，只有满足职业与等级要求的实体能制作。

{
  "id": "core:craft_wood_plank",
  "inputs": [
    { "id": "core:wood", "count": 1 }
  ],
	"target_item": "core:wood_plank",
	"manufacturing_mode": "none",
	"work_amount": 5,
	"processing_difficulty": 0,
	"output_table": "core:wood_plank_output",
	"output_table_executions": 1,
	"compatible_work_points": ["core:workbench"]
}

work_amount 是可选的非负整数基础工时，单位为 1 倍速现实秒；按当前时间尺度，每 1 秒对应 1 游戏分钟。省略或设为 0 时，工作在完成激活、材料预留和到达条件后立即结算。正数工时仍会受到工人的制作速度乘数影响。CoreMod 工作台配方为 15（15 游戏分钟），木板、木地板和木棍为 5（5 游戏分钟）。

生产完成时会触发 recipe:crafted 事件。制作由 CoreMod systems.production 创建生产订单，再由 systems.crafting.queue 发布工作；不存在直接制作入口。

生产订单支持目标次数、维持库存、优先级、指定工人、暂停、恢复和取消。创建生产订单不等于已经创建具体工作：只有材料、合格工人和兼容工作点条件满足时，订单才会向 WorkPool 发布 Craft 工作；命令结果通过 work_created、status 和 waiting_reason 区分两种状态，界面不再显示误导性的“已加入工作池”成功通知。工作激活后才通过统一物品与预留系统绑定材料实例并送入工作点输入暂存；完成时原子提交材料，把产出表结果写入输出暂存。取消或中断会释放预留并安排输入材料返还。

方块定义可用 placeable:true 加入底栏“放置”列表，并可用 placement_duration 指定单格工时；省略时使用正数 hardness。放置目标必须为空、有声明所需的支撑且没有实体/建筑碰撞。每格产生一项 Build 工作，激活时预留一个同 ID 物品，完成时由 Host 校验工作上下文后原子消费并写入体素。placement_support:"below" 可要求目标下方存在方块。CoreMod 树苗声明 growth_target:"core:tree" 和 growth_ticks:600；放置完成后成熟时间写入运行态存档，经过 30 游戏分钟（1 倍速现实 30 秒）且原位置仍为树苗时替换成树。工作台配方消耗 4 木板并产出 1 个可直接放置的工作台方块；core:handcraft 是无需实体建筑工作点的虚拟徒手制作路径，因此第一张工作台不会依赖既有工作台或制作点。徒手制作仍使用权威材料预留与结算；每个成功创建的合成产物都会立即产生幂等的入库搬运工作，周期扫描只负责恢复遗漏。工作台声明下方支撑，因此可以直接落在土、石或人工地板上，而不能贴墙或悬挂。

锻造物品基型（item_bases）

物品基型放在 data/item_bases/。基型 ID 就是目标物品 ID，不再重复配置目标；目标必须存在于 items 或兼容方块物品注册表。基型声明 base_values、base_processing_difficulty、base_materials、attributes、affixes、max_capacity、manufacturing_mode、quality_table 与 compatible_work_points。

每个属性等级直接声明最终增强值 value、capacity_cost 和该等级额外 materials，不会累加前级。词条等级同样声明容量与材料，并可携带 effects、modifiers、manufacturing_events 和 display。具体内容表可以为空；引擎不会填入默认容量、材料、难度或词条。

科技通过 unlocks 中的 item_base:<完整基型 ID> 解锁基型。保存方案只记录基型以及属性/词条的最终等级；修改方案始终生成新的稳定 design ID。无效方案仍可保存并返回具体错误，但不能进入锻造生产。

建筑蓝图（buildings）

建筑定义放在 data/buildings/ 下。建造菜单列出这些建筑蓝图；施工完成后，blueprint 中声明的方块会按建筑原点偏移放入世界。蓝图支持单点 pos，也支持闭区间长方体 from/to。

{
  "id": "copper_age:wood_hut",
  "name": "Wood Hut",
  "size": [5, 5, 5],
  "materials": [
    { "item_id": "copper_age:building_material", "count": 72 }
  ],
  "construction_ticks": 240,
  "blueprint": [
    { "from": [0, 0, 0], "to": [4, 0, 4], "block": "copper_age:floor" },
    { "from": [0, 1, 0], "to": [4, 3, 0], "block": "copper_age:wall" },
    { "pos": [2, 1, 0], "block": "copper_age:door" }
  ]
}

materials[].item_id 和 blueprint[].block 都必须引用已注册方块/物品；所有蓝图坐标都必须在 size 范围内。完整说明见 建筑蓝图注册。

建筑可用 parts 声明内部多体素部件。每项必须包含建筑内唯一的非空 id、非空 type 和非空 cells 坐标数组；坐标必须在建筑 size 内、必须被 blueprint 覆盖，且不同部件不能占用同一格。建筑完成时，CoreMod 以建筑稳定实例 ID 作为 owner 注册部件；每个部件保存稳定实例 ID、定义 ID、实际方块集合和逐格方块 hash，并随版本化运行态及 Host 快照恢复。部件按整体交互和整体移除，不能把各格当作独立对象重复结算。

"parts": [
  { "id": "bed", "type": "bed", "cells": [[0, 0, 0], [0, 0, 1]] }
]

CoreMod 施工入口 systems.construction.order(def_id, x, y, z) 会创建建筑订单；材料足够时立即从 stockpile 账本预留并推进施工，材料不足时返回 { ok=true, status="waiting_materials", materials=..., missing=... } 并等待后续库存补足。等待订单会在 stockpile:changed 后立即重试预留，并每 60 tick 做一次兜底检查。systems.construction.preview_materials(def_id) 可用于只预览材料可用性，不会作为硬阻止。

HTML 建造面板读取 build_defs 快照，行结构为 { id, label, label_key, category, size, cost, materials, missing, available, can_order, status }；已下单建筑读取 construction_active 快照，行结构为 { instance_id, def_id, status, position, materials, missing, reserved_materials }。页面发送 core:build.begin { id } 时进入 placement；只有带 x/y/z 时才实际下单。

殖民者经历（experiences）

经历定义放在 data/experiences/。每条记录声明稳定 ID、名称、质量档位、抽取权重，以及可选的图标、叙事、属性修正、初始职业、工作/战斗/心情/事件反应倾向、初始状态和互斥经历。初始职业与互斥经历会做跨注册表校验。CoreMod 当前可以不提供任何经历条目；引擎不会生成默认经历。

招募生成配置将 0-3 个经历的数量权重作为全局独立分布保存；每个招募等级只提供质量权重、职业总等级下限及高于下限的概率。候选生成前会预检配置，配置无效时不会扣除招募资源。经历附带状态只在候选实体首次创建时施加，招募后经历 ID 与完整候选资料保持持久化。

药材与性状效果（medicinal_herbs / potion_trait_effects）

data/medicinal_herbs/ 每条记录包含 id、name、fire、wind、water 和 earth。data/potion_trait_effects/ 每条记录包含稳定 id、trait（fire/wind/water/earth）、minimum、maximum、effect_id、value、duration 和布尔 positive。两类目录均可为空，不生成默认内容。

effect_id 是生命周期、日志和免疫使用的效果类型标识，不声明覆盖关系。每瓶药创建独立效果组，所有组无条件叠加。效果 ID 必须由 Lua 注册生命周期定义；缺少定义时配置状态在 missing_effect_ids 中给出具体 ID，并报告 potion_effect_definition_missing。

职业（jobs）

职业定义放在 data/jobs/ 下。每项是一个唯一职业树节点，必须声明稳定 career_id、1-5 的 rank、节点前置、工作 tag 和恰好五项 level_abilities；初始 colonist 是无 LEVEL 的特例。普通父链、交叉前置和仅继承不参与转职的 inherited_nodes 分开保存。装备以 equipment:true + supported_jobs 支持具体节点。经验值与四段升级需求只读取唯一 career_progression_rules，内容缺失时不生成公式或心情倍率。

{
  "id": "copper_age:coppersmith_3",
  "career_id": "coppersmith",
  "rank": 3,
  "name": "Coppersmith Apprentice",
  "parent": "core:crafter_2",
  "max_level": 5,
  "prerequisites": [
    { "id": "core:crafter_2", "level": 5 }
  ],
  "allowed_work_tags": ["craft"],
  "level_abilities": [
    { "id": "copper_age:coppersmith_3_level_1", "source_text": "..." },
    { "id": "copper_age:coppersmith_3_level_2", "source_text": "..." },
    { "id": "copper_age:coppersmith_3_level_3", "source_text": "..." },
    { "id": "copper_age:coppersmith_3_level_4", "source_text": "..." },
    { "id": "copper_age:coppersmith_3_level_5", "source_text": "..." }
  ]
}

分配职业成功时会触发 job:assigned 事件。category:"combat" 只标识文档中的战斗职业方向；战斗专项规则未定义时不会自动创建带私有数值的 Squad 或 CombatState，也不存在未定义的区域法力组件。

战斗规则数据（combat）

data/combat/ 仍可作为通用注册目录，但 CoreMod 当前保持为空。专项文档建立前不放入命中、伤害、冷却、压制、法力或外交启动默认值。

战斗接口边界见 战斗接口。

文明（civilizations）

data/civilizations/ 保留注册和运行时接口。NCDOCS 当前没有文明专项玩法和内容表，因此 CoreMod 目录保持为空，不提供私有开局职业、资源、配方加成或文明数值。

{
  "id": "copper_age:copper_clan",
  "name": "Copper Clan",
  "jobs": ["copper_age:coppersmith"],
  "starting_options": [
    {
      "id": "copper_age:starter",
      "blocks": [
        { "id": "copper_age:copper_ore", "count": 4 }
      ],
      "jobs": [
        { "id": "copper_age:coppersmith", "level": 1, "count": 1 }
      ]
    }
  ]
}

焦点事件

焦点是展示给玩家的消息。放在 data/focuses/ 下。条件可以是内置条件（tick_at_least、entity_count_at_least、entity_count_at_most、colonist_need），也可以是 Lua 注册的自定义条件。

{
  "id": "copper_age:copper_found",
  "title": "Copper Discovered",
  "body": "Your colony can start working copper.",
  "severity": "info",
  "one_shot": true,
  "conditions": [
    { "type": "tick_at_least", "tick": 20 }
  ],
  "choices": [
    { "id": "ok", "label": "OK" }
  ]
}

NPC 阵营（factions）

data/factions/ 保留其他殖民地定义 schema；data/name_pools/ 保留名称模板词池。NCDOCS 尚未定义关系上下限、初始关系、影响半径或实例生成规则，因此 CoreMod 当前不提供 NPC 阵营定义，不能把旧示例数值当作稳定玩法契约。

阵营自动生成规则（faction_spawn_rules）

data/faction_spawn_rules/ 保留注册目录，但 NCDOCS 未定义数量、密度、距离或位置生成公式。CoreMod 目录为空，新世界不随机生成 NPC 阵营；旧 Lua/控制台生成入口已移除。

未来有文档依据的专项规则显式加入阵营实例时可发布 faction:spawned 事件；CoreMod 当前不会产生该事件。

外交提议（diplomacy_proposals）

外交提议 schema 放在 data/diplomacy_proposals/。每个文件可定义一个 id、effect、required_status 和可选的 relation_offset、maximum_base_score、treaty_id、forced。当前 NCDOCS 未定义具体外交玩法，CoreMod 目录保持为空，引擎不生成默认提案或积分。

名称池（name_pools）

名称池为未来显式加入的其他殖民地提供名称模板词汇，放在 data/name_pools/ 下。words 必须是字符串数组，空数组会被跳过；名称工具不会自行生成阵营实例。

{
  "id": "copper_age:metals",
  "words": ["Copper", "Bronze", "Tin", "Verdigris"]
}

实体视觉组件

实体原型可以声明 Visual 和 Animation。这两个组件用于客户端渲染，不改变职业、AI、背包等玩法数据。

组件字段说明
Visualmodel, texture, width, height, depthmodel 支持 box 和 biped。贴图路径相对 assets/。
Animationenabled, walk_speed, walk_amplitude, idle_bob当前为 biped 程序动画，按实体水平速度驱动行走摆动。
 
"Visual": {
  "model": "biped",
  "texture": "textures/entities/copper_worker.png",
  "width": 0.45,
  "height": 1.80,
  "depth": 0.45
},
"Animation": {
  "enabled": true,
  "walk_speed": 6.0,
  "walk_amplitude": 35.0,
  "idle_bob": 0.015
}

如果实体贴图加载失败，引擎会使用 missing texture；这不会阻止实体模型和动画渲染。
