网络同步与 Mod 数据

理解 NewColony 的服务器-客户端架构、Mod 数据如何在网络间传输，以及 Lua 脚本怎样在联机环境中正确工作。

网络模型概览

最新目标契约（实现待对齐）：允许短暂字段中间态，保证最终一致；运动发送开始模拟时间、起点和速度向量供客户端外推，运动变化时更新。库存差异补同步，可部分分配的请求先分配可用量再告知缺额。死亡小队操作静默忽略。15 秒未收到有效服务端消息或心跳判掉线；初次进入和重连先准备必要世界状态再开放操作。下面的具体刷新频率和连接细节描述既有实现，不能覆盖本段决定。

逻辑端与物理进程必须分开理解

LogicServer 是玩法权威，LogicClient 是输入与表现端；PhysicalClient 和 PhysicalServer 描述程序的部署形态。逻辑端不是“一台机器”的同义词，也不意味着必须各占一个进程。

运行形态进程内的逻辑端职责
单人世界的 PhysicalClientLogicServer + LogicClient 同时运行本地 LogicClient 提交意图，本地 LogicServer 推进权威世界；不是绕过服务器的单机特例
开放联机的 PhysicalClientLogicServer + 本地 LogicClient同一 LogicServer 同时服务本地和远程 LogicClient
连接远程世界的 PhysicalClientLogicClient连接远程 LogicServer，不独立推进该世界的权威玩法
PhysicalServer可以只有 LogicServer无需 LogicClient、玩家窗口或 UI；这是部署模型，不表示当前独立无界面启动入口已经交付

单人世界可表示为 PhysicalClient { LogicClient ↔ LogicServer }；独立服务端可表示为 PhysicalClient { LogicClient } ↔ PhysicalServer { LogicServer }。即便两端同进程，Lua VM、模块缓存、state 和执行 owner 仍独立。不得根据“运行在 PhysicalClient 中”判断某回调属于 LogicClient。

NewColony 采用 服务器-客户端（Server-Client） 架构。Server 唯一推进游戏逻辑；普通单机也会建立进程内逻辑 Server/Client 回环并复用协议编码、解码、命令和快照路径，不另设可绕过 Server 的单机写入模式。联机时一名玩家作为 Server，其他 Client 连接到该 Server。

加入世界的用户名由客户端提供，当前允许冒名；服务端在玩家选择可加入的殖民地后保存用户名到殖民地实例 UUID 的绑定。原生 C++ 命令由服务器使用该绑定校验，不依赖客户端在命令载荷中提交殖民地 UUID。Mod 自有传输和绕过原生命令入口的调用不受此自动校验。派系定义表示文化来源，同派系殖民地仍各有独立身份与仓储归属。

NetworkSystem 对象本身随 Engine 存活，但活动网络会话属于世界生命周期：创建或读取世界时，WorldLifecycleCoordinator 使用该世界 seed 和当前 Registry 指纹启动 Loopback/Server/Client 会话；返回主菜单时关闭会话并把模式重置为 disabled。主菜单的 Server/Join 操作只记录下一世界的连接配置，不会在尚无世界时提前创建会话；Disconnect 同时清除该配置。这样再次进入世界时不会复用上一个世界的已关闭会话。

角色职责典型操作
Loopback进程内同时承担逻辑 Server/Client；只有 Server 推进模拟普通单机默认自动启用
Server运行完整游戏逻辑、广播快照、处理命令控制台执行 net_server 7777
Client发送 Server 命令、接收快照与命令结果控制台执行 net_join 127.0.0.1 7777
服务器拥有 唯一权威。所有游戏状态（实体位置、血量、背包等）由服务器计算后广播给客户端。客户端的本地修改会被快照覆盖。

快照同步机制

服务器每隔固定 tick 向所有已认证客户端广播一个快照（Snapshot）。快照包含当前 tick 下所有需要同步的实体及其组件状态。

捕获解析属性时，若已有的引擎数值属性因修正溢出等原因无法得到结果，服务器会拒绝该次快照捕获并报告错误；不会静默省略该属性后发送不完整的解析缓存。

两种节奏：实体状态按 snapshot_interval_ticks（默认 2 tick，20 TPS 下 10 Hz）广播；状态通道文档（物品、经济日志、工作池、阵营、设计与存档状态等，由服务器把整个世界序列化成 JSON）按更慢的 state_channel_interval_ticks（默认 20 tick，即 1 Hz）刷新，避免每 2 tick 重复序列化整个世界。full_snapshot_interval_ticks（默认 120）的周期全量快照一定携带通道，因此新加入的客户端最多等待一个通道周期。未刷新通道的那个 tick 不产生任何通道条目，客户端保留已有通道；把"当前包中缺失"当作删除会清空客户端世界状态，这一点由单元测试固定。

增量快照

当启用增量快照（默认开启）时，服务器只发送与上一次快照有差异的实体和被删除的实体。这显著减少了带宽。客户端负责将增量合并到本地完整状态中。

实体组件之外，快照包含版本化领域状态通道。当前覆盖统一物品与仓储策略、目标格及材料预留、工作池、Lua 经营运行态、研究项目、建筑工作点与治疗容量、锻造设计、阵营/双边关系/谈判、要闻定义运行态/活动要闻、经营日志、持续问题和 Server 时间控制；只有内容变化的通道进入增量包。已知 Server 状态通道遇到缺失或未知 schema 会拒绝该次状态应用，不会静默跳过。Client 会清理旧运行态后按 Server 文档完整恢复，暂停/1x/2x/4x/无限速也由 save_state:time_control 覆盖本地显示。CoreMod 的订单、制作、施工、治疗、招募、职业、搬运、药剂、效果、难度、排班等运行态载荷各自携带当前 schema_version = 1；项目尚未发布，不维护旧领域结构的兼容读取。殖民者经历、独立职业履历、待登记状态和药品 CD 槽按实体组件复制。

插值

客户端在两个快照之间可以对 Position 组件做线性插值（lerp），使移动看起来更平滑。统一属性接口查询 position.x/y/z 时返回该插值结果；服务器解析坐标仍随快照传输。

命令系统

客户端通过发送命令（Command）向服务器请求操作。服务器收到后执行命令并更新权威状态，变化会在下一次快照中广播。

命令参数用途
PostTasktask_tag, faction_id, x, y, z, duration, payload_id, priority, designated_worker只接受一次性采掘和采集确认产生的规范 Mine/Chop；Server 会重新校验玩家阵营、目标方块与产出配置、碰撞、优先级、指定者资格和实际路径，其它工作必须从对应来源系统建立。
UiCommandtarget, payload_json把已注册的经营操作提交给 Server 数据桥校验和结算。

block_id 是 32 位方块数据 ID 哈希，与运行时 BlockId 一致；区块差异和实时方块更新也按 32 位传输。

每条命令携带一个递增的序列号。服务器收到后回复 ACK。客户端如果超时未收到 ACK，会自动重发。

经营界面写操作使用同一协议中的 UiCommand，携带稳定 target 和 JSON payload。Client/单机逻辑 Client 只提交命令；Server 调用 CoreMod 数据桥结算，并以 CommandResult 返回原序号和实际结果 JSON。生产、治疗、招募、研究、仓储、区域和地面回收等已定义玩法走该链路。贸易外交当前仅显示接口状态，不发送玩法命令。纯 Client 的基础 ECS、世界方块、Lua data component、runtime state 和统一物品写接口也有底层权限屏障，不能用脚本绕过数据桥。面板开关、筛选、镜头与设计预览等纯本地表示不发送给 Server。

Chunk Terrain Sync

服务器维护 terrain dirty chunk 集合。新客户端连接后会收到 DirtyList，并按 chunk 请求权威端的 delta；单个方块变更也会通过 BlockUpdate 实时广播。

ChunkDelta 由服务器把当前 ChunkSnapshot 与同 seed 生成的原始地形对比得到。生成 delta 时会按 sub-chunk 遍历，完全一致的 sub-chunk 不发送；连续相同 BlockState{id,data} 的修改会编码成 run，短修改保留为单点 entry。客户端解码后把 run 展开到现有 block entry 应用路径，因此应用层仍按 block_index/id/data 写入本地 ChunkDataStore。

握手流程

  1. Client → Hello：客户端发送 peer_name、world_seed、shared_secret、last_applied_tick，以及按 Registry 分类排序的分类 hash 和逐条目 hash。
  2. Server → Welcome：服务器验证密钥、世界 seed 和 Registry 指纹，返回 world_seed、server_tick、authenticated、Server 指纹及明确拒绝原因。分类或条目缺失、条目内容不同都会在进入正常同步前拒绝，并报告具体分类/条目。
  3. Server → ModList + ModDataManifest：握手完全匹配后，服务器发送 Mod 列表（含校验码）和 Mod 数据清单，作为已匹配连接的诊断与兼容通道。
  4. Client → RequestRecords（可选）：客户端对比哈希清单，找出缺失或不匹配的 Mod 数据，向服务器请求这些记录。这里按 Registry 条目比较，不看客户端本地是否安装或启用了对应 Mod：该通道用于让两端持有同一份权威数据，真正的门禁是握手阶段的 Registry 指纹。
  5. Server → Records：服务器发送请求的 Mod 数据原始 JSON（只从服务器已加载内容里取，禁用 Mod 的数据不会被服务）。

只有协议版本、世界 seed 和 Registry 分类/条目指纹全部匹配时，客户端才进入正常快照接收循环。当前未发布协议重置为 v1，只包含现行实体字段、专项 Mine/Chop PostTask、Server UiCommand 和领域快照；背包、装备和物品位置只走统一物品领域快照。协议版本由包头严格校验；seed 或 Registry 不一致不会通过后续记录交换掩盖。

Mod 列表与校验码

side 字段

mod.json 支持 "side" 字段，标记 Mod 的运行环境：

值含义影响校验码
"client"仅客户端（UI、音效替换等）否
"server"仅服务端（后台逻辑等）否
"both"（默认）影响游戏逻辑，双方都需要是

未填写 side 时默认为 "both"，向后兼容。

校验码（Checksum）

引擎对当前已加载内容中所有 side == "both" 的 Mod（按加载顺序）计算一个 64-bit FNV-1a 哈希值，作为ModList 校验码。校验码仅基于 Mod 的 id 和 version，不包含数据内容。

“已加载内容”= 启用并被 load_all() 成功加载的 Mod：禁用但已安装的 Mod、因依赖或校验失败被跳过的 Mod 都不在校验码里，也不在 ModList 包与 mod_list / export_mod_list 输出中；存档 mods.json 会列出所有已安装 Mod，但它们的 enabled 为 false。包内的 mod_count/mods 和 checksum 始终描述同一批 Mod。启用或禁用 Mod 后需要重启才会改变加载结果与校验码。

Lua 脚本在网络中的行为

服务器上的 Lua

作为服务器的玩家运行完整的游戏逻辑。Lua 脚本的所有行为与单机模式一致：on_tick 每帧执行、事件正常触发。服务器 Lua 可通过 engine.entities.spawn(id) 或 engine.entities.spawn(id, payload) 生成实体；生成结果会进入 Server 快照。

客户端上的 Lua

纯客户端不推进本地玩法模拟，游戏状态由服务器快照驱动。底层 Lua 写接口会在执行前固定拒绝，而不是先改本地状态再等待快照覆盖。拒绝范围包括 ECS、方块、data/runtime state、工作和预留、统一物品、建筑施工/治疗容量、设计方案、研究、要闻、经营日志/问题以及阵营关系和外交结算。视图、选择、蓝图编辑、本地语言和内容注册不属于 Server 权威玩法状态。

区分服务器和客户端

engine.network.mode() 返回 server、client 或 disabled，只用于选择表现和诊断分支。纯 Client 不执行玩法 on_tick；玩家操作应调用现有的 engine.ui.command.run(target, payload)，由数据桥把已注册的 Server 权威 target 编码成 UiCommand。

常见错误：尝试直接发移动、方块或给物命令，或直接写组件。此类入口不存在；玩法请求必须使用已注册、由 Server 处理的专项 UiCommand。

重连与恢复

客户端断线后自动尝试重连（最多 10 次，指数退避）。会话记录在服务器内存中保留 60 秒。

编写网络兼容 Mod 的最佳实践

  1. 影响游戏逻辑的 Mod 用 "side": "both"。纯客户端 Mod（UI 主题、音效包）应用 "side": "client"，这样它们不会影响校验码。
  2. 在服务器上修改状态，客户端只发命令。
  3. 数据文件保持确定性。不要在 Lua 中使用 math.random（已禁用），使用 engine.random。
  4. 使用 mod_list 和 export_mod_list 命令调试。对比服务器和客户端的 Mod 列表和校验码是否一致。主菜单的 MOD 管理器 也会显示当前 ModList、校验码和加载顺序，并可导出 ModList JSON。
