网络同步与 Mod 数据

理解 NewColony 的主机-客户端架构、Mod 数据如何在网络间传输，以及 Lua 脚本怎样在联机环境中正确工作。

网络模型概览

NewColony 采用 主机-客户端（Host-Client） 架构。一名玩家作为主机（Host），同时运行游戏逻辑和服务器；其他玩家作为客户端（Client）连接到主机。

角色职责典型操作
Host运行完整游戏逻辑、广播快照、处理命令控制台执行 net_host 7777
Client发送命令、接收快照、预测与回滚控制台执行 net_join 127.0.0.1 7777
主机拥有 唯一权威。所有游戏状态（实体位置、血量、背包等）由主机计算后广播给客户端。客户端的本地修改会被快照覆盖。

快照同步机制

主机每隔固定 tick 向所有已认证客户端广播一个快照（Snapshot）。快照包含当前 tick 下所有需要同步的实体及其组件状态。

Speedx, y, z

组件是否被同步由组件掩码（Component Mask）决定。客户端收到快照后，根据掩码逐字段覆盖本地状态。

增量快照

当启用增量快照（默认开启）时，主机只发送与上一次快照有差异的实体和被删除的实体。这显著减少了带宽。客户端负责将增量合并到本地完整状态中。

插值

客户端在两个快照之间可以对 Position 组件做线性插值（lerp），使移动看起来更平滑。

命令系统

客户端通过发送命令（Command）向主机请求操作。主机收到后执行命令并更新权威状态，变化会在下一次快照中广播。

命令参数用途
MoveEntityentity_id, x, y, z移动实体
BuildBlockx, y, z, block_id放置方块
MineBlockx, y, z挖掘方块
AssignProfessionentity_id, profession_id, level分配职业
GiveBlockentity_id, block_id, count给予方块物品
PostJobjob_type, faction_id, x, y, z, duration, data发布工作到主机 WorkPool

block_id 是 32 位方块数据 ID 哈希，与运行时 BlockId 一致；区块差异和实时方块更新也按 32 位传输。

每条命令携带一个递增的序列号。主机收到后回复 ACK。客户端如果超时未收到 ACK，会自动重发。

Chunk Terrain Sync

主机维护 terrain dirty chunk 集合。新客户端连接后会收到 DirtyList，并按 chunk 请求权威端的 delta；单个方块变更也会通过 BlockUpdate 实时广播。

ChunkDelta 由主机把当前 ChunkSnapshot 与同 seed 生成的原始地形对比得到。生成 delta 时会按 sub-chunk 遍历，完全一致的 sub-chunk 不发送；连续相同 BlockState{id,data} 的修改会编码成 run，短修改保留为单点 entry。客户端解码后把 run 展开到现有 block entry 应用路径，因此应用层仍按 block_index/id/data 写入本地 ChunkDataStore。

握手流程

  1. Client → Hello：客户端发送 peer_name、world_seed、shared_secret、last_applied_tick。
  2. Host → Welcome：主机验证密钥，返回 world_seed、server_tick、authenticated 标志。
  3. Host → ModList + ModDataManifest：认证通过后，主机发送 Mod 列表（含校验码）和所有 Mod 数据的哈希清单。
  4. Client → RequestRecords（可选）：客户端对比哈希清单，找出缺失或不匹配的 Mod 数据，向主机请求这些记录。
  5. Host → Records：主机发送请求的 Mod 数据原始 JSON。

握手完成后，客户端进入正常快照接收循环。收到 Records 后，客户端会用 reload 语义写入本地 Mod 注册表，并刷新实体原型、配方、职业、地形数据、建筑、区域和渲染世界资源等由注册表派生的运行时缓存。

Mod 列表与校验码

side 字段

mod.json 支持 "side" 字段，标记 Mod 的运行环境：

值含义影响校验码
"client"仅客户端（UI、音效替换等）否
"server"仅服务端（后台逻辑等）否
"both"（默认）影响游戏逻辑，双方都需要是

未填写 side 时默认为 "both"，向后兼容。

校验码（Checksum）

引擎对所有 side == "both" 的 Mod（按加载顺序）计算一个 64-bit FNV-1a 哈希值，作为ModList 校验码。校验码仅基于 Mod 的 id 和 version，不包含数据内容。

Lua 脚本在网络中的行为

主机上的 Lua

作为主机的玩家运行完整的游戏逻辑。Lua 脚本的所有行为与单机模式一致：on_tick 每帧执行、事件正常触发。spawn_prototype 创建的实体会出现在快照中。

客户端上的 Lua

客户端的 Lua 脚本同样会运行，但游戏状态由主机快照驱动。客户端对组件的本地修改会被下一次快照覆盖。客户端应该通过命令请求主机执行操作，而不是直接修改本地状态。

区分主机和客户端

function M.on_tick(tick, dt)
  local mode = engine.network.mode()   -- "host", "client" 或 "disabled"
  if mode == "host" or mode == "disabled" then
    engine.ecs.set_position(entity, x, y, z)
  elseif mode == "client" then
    engine.network.send_move(entity, x, y, z)
  end
end
常见错误：在客户端 on_tick 中直接修改 Position、Health、Inventory 等同步组件。这些修改会被快照覆盖，导致"闪烁"或状态丢失。

重连与恢复

客户端断线后自动尝试重连（最多 10 次，指数退避）。会话记录在主机内存中保留 60 秒。

编写网络兼容 Mod 的最佳实践

  1. 影响游戏逻辑的 Mod 用 "side": "both"。纯客户端 Mod（UI 主题、音效包）应用 "side": "client"，这样它们不会影响校验码。
  2. 在主机上修改状态，客户端只发命令。
  3. 数据文件保持确定性。不要在 Lua 中使用 math.random（已禁用），使用 engine.random。
  4. 使用 mod_list 和 export_mod_list 命令调试。对比主机和客户端的 Mod 列表和校验码是否一致。主菜单的 MOD 管理器 也会显示当前 ModList、校验码和加载顺序，并可导出 ModList JSON。
